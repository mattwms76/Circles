# OAuth callback and error states — design audit

**Scope:** `/oauth/callback` only. Captures are signed-out/missing-parameter gates; processing, success, provider-error, and redirected/authenticated states were source-reviewed and **not** visually verified. No server, browser, sign-in, data mutation, or test suite was run.

## Visually confirmed

- **Consistent, centered geometry across all supplied sizes.** The error block is centered at 320×740, 390×844, 768×1024, and 1440×1000; there is no visible overlap, clipping, horizontal overflow, header/tab occlusion, card/media geometry, or doubled outer gutter. Metrics report `documentWidth === viewport width` and no off-screen text for all four captures.
- **Readable hierarchy and identity.** Heading is 20px/28px bold coral and body is 16px/24px, meeting the stated body/secondary goals while preserving the coral-on-cream identity. The 20px horizontal content padding from `p-5` leaves ample room: the longest captured line is 252px wide at 320px viewport (34px x-origin).
- **Vertical rhythm is visibly spacious rather than cramped.** The measured 24px gap between heading and message is stable in every capture (heading y 332/384/474/462; message y 384/436/526/514). There are no fixed overlays or keyboard interactions visible in this static, control-free state.

## Issues and source risks

| Severity | File:line | Finding | Evidence | Minimal fix |
|---|---|---|---|---|
| **Medium** | `app/oauth/callback.tsx:156-164` | Error state has no recovery affordance: it only renders a heading and message, so an expired/malformed callback leaves the user stranded with no retry, back-to-app, or close action. This also means there is no actionable 44px touch target in the error mode. | Visually confirmed in all four captures: exactly two text nodes and `controls: []`; the screen cannot advance from “Authentication failed.” | Add a clearly labeled, full-width or naturally sized `Button`/`Pressable` (minimum 44px height) such as “Try sign in again” that restarts the auth flow or routes to the signed-out entry screen; optionally add “Back to Circles.” Keep the existing coral/cream treatment. |
| **Medium (source risk)** | `app/oauth/callback.tsx:92-100,156-163` | Provider-supplied `error` is rendered verbatim. Long/localized or maliciously verbose callback errors can create an unexpectedly tall block and poor hierarchy; there is no normalization, max length, or explicit constrained text width. | Captures only cover the short fallback “Missing OAuth callback parameters”; provider-error and long-text modes were not captured, per the signed-out gate constraint. | Map known OAuth error codes to concise, user-facing copy; otherwise truncate/sanitize to a bounded message and render it in a `Text` with `maxWidth: 520`, `textAlign: "center"`, and an accessible expansion/details path if needed. |
| **Low (source risk)** | `app/oauth/callback.tsx:137-145` | Processing mode adds both parent `gap-4` and `mt-4` to the status text, producing roughly 32px between spinner and copy (a likely doubled spacing token). This state was not visible in the supplied missing-parameter captures. | Source shows `ThemedView ... gap-4` plus `Text className="mt-4"`; processing is conditional and not visually verified. | Remove `mt-4` or remove the parent gap for this fragment; use one intentional 16px spacing token and retain centered 16px/24px copy. |
| **Low (source risk)** | `app/oauth/callback.tsx:147-154` | Success mode has two separate 16px/24px text rows plus parent `gap-4`; the resulting 16px inter-line gap may read as two unrelated messages and delays the 1-second redirect without communicating progress. | Success mode is source-only; no successful OAuth capture was available. | Use one concise success message (or a single text block with deliberate line break) and, if the redirect remains delayed, add a small progress indicator or explicit “Opening your circles…” copy; preserve the 1-second redirect behavior unless product requirements differ. |
| **Low (source risk)** | `app/oauth/callback.tsx:136-137` | `SafeAreaView` applies all safe-area edges while the centered content also has fixed `p-5`. On devices with substantial horizontal/vertical insets (especially landscape or keyboard-adjacent return), the effective content inset can become unnecessarily large; this cannot be assessed from the clean portrait captures. | Source uses `edges={["top","bottom","left","right"]}` plus `p-5`; supplied captures show no safe-area anomaly, keyboard, or overlay. | Keep safe-area handling, but constrain it to the platform-relevant edges/orientations or use a single inset-aware content padding strategy; verify landscape and keyboard-return states before changing. |

## Coverage notes

- **Breakpoints:** This route has no route-specific breakpoint logic; all four widths render the same centered composition without visible responsive defects. Shared `AppShell` header/sidebar/tab behavior is not used by this screen.
- **Moderation, editing, overlays, active conversations/live sessions:** Not applicable to this OAuth callback route. No claims are made about gated signed-in states; those require source review (done for this file) rather than visual verification.
- **Touch targets:** The current error screen intentionally has no interactive controls, but that is the recovery issue above—not a compact-badge violation. Any added action should be at least 44px high and keyboard/safe-area tested.
