Circles · product and engineering review · 15 October 2026

Make the existing experience dependable, clear and worth returning to.

Circles is a feature-rich pre-beta app. The strongest next investment is proving its native journeys, completing community safety and running a focused hosted pilot. Additional features should follow evidence from that pilot.

This is an analysis and implementation plan. No app code, production configuration or database was changed during this review.

There is already substantial functionality

The React Native app includes public/private circles, memberships and roles; personalized and chronological feeds; photos, video recording/editing and drafts; 24-hour stories; comments, replies and reactions; DMs and circle chat with media; polls/questions; topics and collections; invitations; recognition; catch-up; events; live-room and wallet integrations; notification controls; blocking, reports and account deletion.

Light/dark appearance, shared color tokens, reduced motion, accessible labels and several virtualized lists are already present. The next design pass should improve hierarchy and test real-device behavior while retaining these foundations.

The latest security remediation record reports deployed fixes for all eleven findings. The last recorded live verification, at 14:26 UTC on 15 October, found RLS on all app tables and no Security Advisor warnings/errors. It also recorded zero Auth users, profiles and Storage objects. These are timestamped prior results; this review did not re-query production.

Positioning recommendation: build around interest-based communities where members receive useful responses and recognize familiar people. Existing prompts, polls, collections and catch-up support that direction. A successful first conversation is a better early product goal than adding another feed format.

Implementation scope and acceptance

A01 · P0Confirmed maintenance gap

Establish one release baseline

Many app, security, backend and test changes are still modified or untracked locally. README sections contradict each other on test counts, deployment status, authentication and scheduled services. Remote migration entries are bundled differently from the historical local files.

Implement
Review and version the Circles changes in coherent commits, preserve the unrelated Windows utility locally, and produce a release manifest tying source revision, schema, function hashes and native build together. Consolidate current status and archive historical notes. Document the canonical bootstrap and upgrade path, compare resulting schemas/privileges, and rehearse an upgrade in staging. Do not blindly replay historical migrations or repair history metadata without reconciliation.
Done when
A fresh checkout installs with the frozen lockfile, passes code/security/Edge checks and the disposable Auth/REST/Storage CI suite, and reproduces the release schema. Fresh install and upgrade yield matching app schema and grants. Current release documentation has one consistent status and a safe rollback/forward-repair procedure.
Dependencies
No new service credentials for local consolidation; GitHub CI and a disposable staging environment for integration evidence.
Evidence: README, checks workflow, bootstrap manifest, current Git status, database audit.
A02 · P0Confirmed coverage gap

Complete the community safety workflow

Report types currently cover posts, profiles, circles, DMs and live sessions. There are no dedicated comment, story or circle-chat-message targets. Circle-chat “Report message to circle moderators” actually submits a circle report, with the message ID embedded in free text; the queue is authorized for global moderators. Removal actions cover only posts, DMs and live rooms.

Implement
Add typed report targets and precise content references for comments, stories and group messages, with a permission-checked review preview and removal flow. Define circle-host versus staff escalation responsibilities, truthful action labels, audit trails, report status and appeals/contact routes. Limit access to private content to authorized case reviewers. Define objectionable-content filtering and review rules, public community standards, versioned terms acceptance before uploading, privacy/support links, and an explicit audience/age-safety decision. Assign named staff reviewers before inviting users.
Done when
Every supported content type can be reported and handled end to end; non-reviewers cannot fetch case evidence or perform actions. Tests cover removed/expired content and lost membership. A test report reaches the right queue, is acted on and leaves an audit record. Policies/contact are reachable from onboarding and Settings; acceptance is enforced server-side at the relevant publication boundary.
Dependencies
Product decisions on audience and moderation policy; operator-provided support contact and named reviewers. Filtering-provider selection, if needed, requires a separate cost/privacy review.

This is a store-readiness issue as well as a product gap. Apple describes filtering, reporting, blocking and contact requirements; Google also requires terms acceptance before UGC creation. See Apple UGC guidance and Google Play UGC policy. These checks do not guarantee store approval.

Evidence: report constraint, circle-chat reporting, moderator UI and Settings, review_report and moderation_queue.
A03 · P0Verification gap

Prove operational recovery and account delivery

Working scheduled jobs and hardened access policies are recorded. A usable database recovery window, media recovery procedure, Auth administrative settings and production email delivery have not been established by the available evidence.

Implement
Confirm actual backup coverage and recovery points; agree acceptable data loss and recovery time; back up media separately and rehearse restoration into a disposable project. Verify staff MFA, Auth password/leak protection and abuse protection, SMTP/domain authentication and confirmation/recovery deliverability. Rotate the previously shared old-project database password and update any consumers. Add named incident ownership and alerts for failed cron/notification/cleanup jobs and unusual storage/egress growth.
Done when
A documented restore drill recovers representative relational data and its media, preserves access controls and meets the agreed recovery objectives. Email signup/recovery succeeds in test inboxes. A deliberately failed staging job produces an actionable alert. Administrative checks and credential rotation have operator evidence.
Dependencies
Administrative dashboard access, backup/storage budget decisions and email-domain ownership. Current settings must be checked before changing them; unavailable API scope does not mean a protection is disabled.

Supabase database backups contain Storage metadata, not the underlying uploaded files. See backup scope and production checklist.

A04 · P0Release gate

Validate real native builds and gate unfinished services

The browser preview uses simulated HTML/JavaScript. JavaScript bundle exports and mocked SDK tests cannot prove native camera, Keychain, push, Agora or store behavior. The current release checker still flags three deferred configuration values.

Implement
Create signed iOS/Android development builds. Run the existing device checklist with two real test accounts: denied permissions, record/trim/upload, interrupted network, app backgrounding, account switches, old-session migration, offline logout, reinstall, stories, DMs, deletion and private links. Complete EAS/APNs/FCM, Agora and store products when supplied. Make availability explicit in the UI, preserve legitimate core use when an optional service is unavailable, and prevent a production release advertising incomplete services. Test store purchases against an isolated test backend/ledger, retaining production rejection of sandbox credits.
Done when
Each supported device/OS journey has build-specific results and evidence; no critical privacy, data-loss or navigation defects remain. Push delivery, live sessions and real store testing pass before their features are advertised as enabled. Missing configuration produces understandable availability feedback.
Dependencies
EAS project/signing access, Agora credentials, store setup, iOS and Android devices. These were deferred by the owner; independent work in A01–A03 and A05–A11 can continue.
Evidence: release gate, device acceptance checklist, authored device flow, native security verification still required.
A05 · P1Design hypothesis to test

Reduce competing controls across screens

The existing theme and typography scales are useful. Source inspection shows several layers of feed controls, circle actions and tool disclosures. The opportunity is a clearer order of importance; no fresh pixel-level or physical-device visual audit was performed in this review.

Implement
Home: give feed content and one creation action priority; keep secondary preferences in one predictable place. Circles: show identity, join state and timeline first, then a compact route to chat/library/events; show host tools only for appropriate roles. Inbox: make the DM/circle-chat distinction and filter scope explicit. Profile/Settings: group community identity, preferences, safety and support. Live/wallet: explain unavailable services and costs before actions. Standardize recurring button states, body text, spacing and sheet keyboard behavior using existing tokens.
Done when
The full screen/state inventory is reviewed at narrow widths, maximum supported text size, light/dark, reduced motion, VoiceOver and TalkBack. No clipped actions or horizontal overflow; focus returns sensibly when sheets close. In a small task-based usability session, users find a circle, publish, locate a reply and report content without coaching; record failures rather than assuming visual changes improved usability.
Dependencies
Agreed screen hierarchy; real native QA from A04 for final acceptance.
Evidence: existing theme scales, Home/Explore, feed and circle controls, prototype screen checks.
A06 · P1Confirmed source risk

Make message history and inbox filtering coherent

DM pagination orders by creation time and fetches older rows with created_at < before. Circle chat also uses a timestamp-only boundary despite a secondary ID sort. At a page boundary containing equal timestamps, remaining tied rows can be omitted. Inbox name/unread filters apply to DMs; the circle-chat list receives neither filter.

Implement
Use stable composite (created_at,id) cursors and matching order for both chat types. Preserve scroll position and merge realtime rows without duplicates while paging or reconnecting. Choose either unified search/unread across both lists or clearly labeled DM and Circle tabs with independently correct controls. Virtualize growing conversation lists after profiling.
Done when
A fixture with more than a page of identical timestamps is traversed completely exactly once. Concurrent incoming messages, deletion and reconnect do not drop or duplicate rows or jump the reading position. Search and Unread behavior matches its visible label for both chat types; two-account native tests pass.
Dependencies
No missing external credentials for query/UI changes; A04 for transport/device acceptance.
Evidence: loadConversationMessages, circle message loader, InboxScreen, GroupInbox.
A07 · P1Usability enhancement

Explain media constraints and recovery before failure

Resumable uploads, progress, cancellation, retry and retained drafts already exist. Videos are limited to two minutes and 25 MB. The security migration adds account quotas, while local draft media lives in a cache that the OS may reclaim.

Implement
Add a small publishing-status view for saved, uploading, paused, failed and published work; route users back to existing drafts. Explain file/duration limits before recording, map server rate/quota errors to actionable copy, and offer re-selection when cached media disappears. Show account storage usage through an ownership-scoped summary. Investigate compression/format normalization with representative iOS/Android clips before selecting a library or backend service. Preserve edited originals until the replacement is validated.
Done when
Network drop, process restart, lost publication response, missing cached file, exhausted quota and expired pending upload each have a tested recovery route. Retries create one post, and the correct circle is retained. Text survives even if a video must be reselected. Measured compression preserves acceptable quality and does not bypass server validation.
Dependencies
A04 for device formats and interruptions. Any transcoding service needs a separate budget and privacy decision; the upload manager must not promise background execution the OS has not granted.
Evidence: TUS retry, draft retention, composer, quotas and pending-upload expiry.
A08 · P1Acquisition and recovery enhancement

Finish sharing and authentication handoffs

Expiring/revocable HTTPS invitation pages and custom-scheme content links exist. Native verified HTTPS links and store-install fallbacks are not configured. The hardened PKCE flow intentionally requires a recent request on the initiating device.

Implement
Configure Universal Links/App Links on an owned domain with correct signing associations; offer accurate installed/uninstalled/expired/private invitation states. Retain intended destinations safely through login and membership approval. Explain expired or cross-device Auth links and provide a way to start a fresh confirmation/recovery on the current device. Validate outbound authentication email templates and scanners without weakening PKCE or adding broad redirect wildcards.
Done when
Installed and uninstalled iOS/Android devices, signed-in/out accounts, private pending members, expired invites and wrong-device recovery each reach a safe, clear next step. Links never disclose private-circle content or replace an existing signed-in account silently.
Dependencies
Owned domain, signing fingerprints, store listings for install buttons, and SMTP access. UX/error handling can be implemented before those values exist.
Evidence: content link routes, PKCE initiation checks, existing invitation landing page, native link configuration.
A09 · P1Product hypothesis

Launch a hosted pilot with a clear first success

The last database audit found six ownerless starter circles, including a private circle, and no global moderators. Existing onboarding, weekly prompts, helpful-answer recognition and catch-up can support a pilot once real hosts exist.

Implement
Choose two or three initial interests with explicitly nominated hosts and staff reviewers. Recheck starter-circle ownership; assign each retained circle to an approved real host with matching membership, or archive it. Never promote the first signup automatically. Add a welcome post, useful collection and weekly activity schedule. Guide onboarding from interest selection to joining an active circle and answering one approachable prompt. Give hosts a simple unanswered-post/new-member checklist using existing data, with quiet-hours-respecting reminders.
Done when
Every visible pilot circle has a reachable accountable host; private membership requests can be decided. New members can complete join and first contribution, and hosts can identify unanswered contributions. A small invited cohort supplies observed usability and return-visit evidence before adding more categories.
Dependencies
Named hosts and staff; A02–A04 safety and device gates before a wider pilot.
Evidence: starter-circle ownership finding, existing onboarding, prompts, recognition and catch-up.
A10 · P1Measurement gap

Measure activation, reliability and cost

The app already has opt-in scrubbed diagnostics and a staff-only 30-day activation summary. Those counts do not establish retention cohorts, time to first response, upload success, latency or the cost of serving active communities.

Implement
Define a small documented metric dictionary and privacy/retention rules. Prefer aggregates derived from existing records; add consented minimal events only where required. Track join-to-contribution, first helpful response, return participation, upload outcomes and service error/latency. Add actionable alert ownership and build/release identifiers. Profile feed/chat queries and native lists using a representative staging dataset; load-test anticipated pilot concurrency and record database, media egress, Realtime and live-room costs.
Done when
A staff dashboard can answer whether members receive replies and return, while excluding content/token payloads from telemetry. A versioned report records device/network/data-size conditions, p50/p95 latency, errors and estimated operating cost. Performance tuning follows measured slow paths; rate and quota changes have observed justification.
Dependencies
A09 for real product baseline; A03 for alert routing. Do not load-test production or treat zero-user measurements as capacity proof.
Evidence: opt-in error diagnostics, activation_metrics, Supabase staging/load guidance.

A12 · P2Validate before expansion

Add depth where pilot users demonstrate a need

A12a · Search within community knowledge
Extend existing people/circle discovery with permission-aware post/topic/collection search and useful result snippets. Start only if members cannot retrieve existing answers. Acceptance: private/blocked/removed content never leaks, paging is stable, and tested tasks are faster than the present library flow.
A12b · Assisted video captions
Manual timed captions already exist. Investigate optional transcription with editable results, clear consent, supported languages and predictable costs. Acceptance: edits persist through retry and playback; speech is not sent to an external provider without the agreed disclosure/choice; accessibility and quality are checked on representative clips.
A12c · Personal data export
Add a reauthenticated account export with a clear scope, private short-lived delivery, retention/deletion rules and a visible progress state. Acceptance: an account can export its eligible data without receiving other members' private data or privileged audit evidence; expired downloads fail safely.
Dependencies and gate
A02/A03 security and operational rules, A10 evidence, and a short scope/cost proposal for each. Ship each as an independent small release only after the product owner selects it. These are enhancements, not diagnosed regressions.

How to judge improvement

Collect a pilot baseline before choosing retention or growth targets. Suggested initial operating goals below are proposals for Circles, not measured current performance or industry benchmarks.

  • Activation: percentage of new members who join a circle and make a contribution in seven days; distinguish public joins from private approvals.
  • Community value: time to first response and share of new contributions receiving another person's reply within 24 hours. Proposed host goal: acknowledge every pilot member's first contribution within 24 hours.
  • Return use: seven-day return participation by signup cohort and circle, showing denominators and avoiding conclusions from tiny samples.
  • Reliability: completed uploads / attempts, recoveries after interruption, crash-free sessions where consent permits measurement, message-history completeness and p95 journey latency under recorded conditions.
  • Safety: report routing success, first-review/resolution time and oldest unreviewed case. Proposed staffed-pilot goal: first review within 24 hours, with urgent escalation separately defined.
  • Cost: storage and egress per active member, notification/Realtime failures and live cost per participant-minute. Set budget alerts before widening access.

Release gates remain behavioral: zero known critical authorization/data-loss issues, passing core native journeys, working support/moderation and a successful recovery rehearsal. A growing test count alone is insufficient evidence.
