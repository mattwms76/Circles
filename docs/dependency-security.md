# Dependency security policy

The dependency graph is resolved with **pnpm 9.12.0** and the repository’s existing lifecycle allowlist: `esbuild` and `unrs-resolver`. Security changes must use a supported parent release or a version-scoped override. They must not use `--ignore-scripts`, audit ignores, an unused direct dependency, or a blanket major override.

## Applied compatible resolutions

The lock uses supported same-line fixes for `@babel/core`, `@humanfs/node`, `@xmldom/xmldom`, `ajv`, `baseline-browser-mapping`, `brace-expansion`, `browserslist`, `compression`, `flatted`, `js-yaml`, `minimatch`, `mysql2`, `nanoid`, `node-forge`, `picomatch`, `postcss`, `source-map-js`, `ws`, and `yaml`.

Three formerly residual families now have narrow, tested parent overrides. `@esbuild-kit/core-utils>esbuild` resolves `0.25.12`, which is patched for [GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99). `@expo/ngrok>uuid` and `xcode>uuid` resolve `13.0.1`, which is patched for [GHSA-w5hq-g745-h8pq](https://github.com/advisories/GHSA-w5hq-g745-h8pq). `postcss-nested>postcss-selector-parser` and `tailwindcss>postcss-selector-parser` resolve `7.1.6`, which is patched for [GHSA-rj75-hqrm-r3gf](https://github.com/advisories/GHSA-rj75-hqrm-r3gf). These are intentionally scoped to the actual consumers rather than blanket package-major overrides.

`uuid@13.0.1` is ESM. Node 22.23.4 synchronously loads its named exports through the two legacy CommonJS consumers, and the focused test calls `v4()` and `validate()` through each consumer before loading Expo ngrok and xcode. `@esbuild-kit/core-utils` runs both `transformSync` and `transform` on synthetic TypeScript. The NativeWind check runs a `postcss-nested` selector conversion and a Tailwind utilities build with the `nativewind/preset`. No Expo SDK 57 or React Native 0.86 upgrade was made.

`ws` intentionally keeps both consumer-supported majors: Expo CLI/tunnel resolves `8.21.0`, while React Native and Metro tooling resolve `7.5.11`. `@xmldom/xmldom` remains on the Expo-compatible 0.8 line at `0.8.15`. `node-forge` is limited to `1.4.0`, which fixes four earlier advisories but not the separately listed no-patch advisory below. `mysql2` remains a dependency for the guarded archival migration utility at `^3.23.1`; this does not introduce a MySQL runtime fallback.

`tests/dependency-security.test.ts` is credential-free. It covers the parent-resolved versions, the four compatibility probes above, the explicit decode malformed-URL regression, an in-memory plist round trip, and a synthetic in-memory certificate corruption rejection. It does not use signing material, database credentials, native devices, or provider services.

## Explicit residuals

The [compact audit summary](./dependency-audit-summary.json) retains **four records in four families**: three high and one moderate. The full raw registry response was not saved or printed; the audit stream retained only the seven in-scope GHSA identifiers.

- `braces@3.0.3` — high, [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), path `expo@57.0.24 > @expo/cli@57.0.26 > @expo/metro-file-map@57.0.3 > micromatch@4.0.8 > braces@3.0.3`; it also occurs under development Tailwind `chokidar` and `micromatch`. There is no patched release. No committed app source imports it. A vendor recursion rewrite was not applied because it could change framework glob semantics. Build patterns must remain repository-controlled; this reachability limitation is not a resolution.
- `http-cache-semantics@4.2.0` — high, [GHSA-ch52-4w7c-c8xp](https://github.com/advisories/GHSA-ch52-4w7c-c8xp), development-only path `@expo/ngrok@4.1.3 > got@11.8.6 > cacheable-request@7.0.4 > http-cache-semantics@4.2.0`. No committed app source imports it and no maintainer fix exists. No third-party tunnel cache-behavior patch is applied; development tunnel traffic is not evidence that this is resolved.
- `node-forge@1.4.0` — high, [GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv), path `expo@57.0.24 > @expo/cli@57.0.26 > node-forge@1.4.0` (also through `@expo/code-signing-certificates`). The app has no direct import and no patched release exists. Do not pass untrusted RSA PKCS#1 v1.5 signatures to this tooling path or relax TLS/signature verification. A custom RSA or ASN.1 verifier patch is explicitly out of scope and would not be safe evidence of remediation.
- `decode-uri-component@0.2.2` — moderate, [GHSA-vcc3-ghjq-m6fr](https://github.com/advisories/GHSA-vcc3-ghjq-m6fr), path `expo@57.0.24 > expo-router@57.0.22 > query-string@7.1.3 > decode-uri-component@0.2.2`. The maintainer fix is `0.5.0`, but it is ESM default-export-only while `query-string@7.1.3` CommonJS requires a callable decoder. The compatibility test preserves the current malformed `%E0%A4%A` fallback behavior. No unsafe override, wrapper, or fake clean audit was applied. Any request path that exposes this consumer to attacker-controlled query text needs a bounded input policy; that mitigation does not resolve the record.

### Decoder 0.5.0 bridge safety gate

The exact published `decode-uri-component@0.5.0` source was checked against the npm artifact (`index.js` SHA-512 `fa5312a2d7b4bf9bce427910955747a856673d4ae15e7ff70a03e234d33cfb6b4817439f9e0d40df2775383a15d7bcad72e4dd1e10d8b060ee7fc12ee603e016`). A local MIT-licensed CommonJS candidate was generated from that unchanged source with esbuild, retained `index.js` for the `import` condition, and exposed the generated callable only through a `require` condition. Direct CJS and original ESM returned the same values for malformed input, a lone percent sign, UTF-8, and emoji; the bounded 200-token `%ab` CVE pattern also completed with the fixed decoder.

It is **not a safe project fix in the current installation topology**. With the repository’s `node-linker=hoisted`, pnpm 9.12.0 recorded the exact `patchedDependencies` entry in the lock but installed the original `0.5.0` package without `index.cjs` or the `require` condition. The real `query-string@7.1.3` consumer then raised `TypeError: decodeComponent is not a function`. The override, patch entry, generated patch, and resulting lock changes were removed rather than shipping a lockfile that claimed a patch which the installed consumer did not receive. No decoder algorithm was written or substituted.

## Patches requiring upstream review

Wait for a maintainer patch or a consumer-compatible parent migration for `braces` and `http-cache-semantics`. For `node-forge`, review only an official strict `DigestAlgorithm` ASN.1 validation fix; do not hand-roll cryptography. For `decode-uri-component`, migrate the `query-string`/Expo Router consumer to an ESM-compatible parent before replacing the decoder, or first demonstrate that an exact pnpm patch is physically applied under the repository’s production linker. Every future update must re-run the frozen install, focused consumer tests, credential-free type check, and an in-scope registry audit. A resolved top-level package name is not evidence that every affected transitive copy is patched.
