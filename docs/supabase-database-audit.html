Circles Supabase database audit

15 October 2026 · Project vvclcsqletcxzoaayqzq · Catalog snapshot at 14:18 BST; follow-up checks and isolated reproductions completed afterward.

Seven actionable findings: one high priority and six medium priority. The public-circle membership policy permits self-assigned moderator roles. Fix this before onboarding real users. Supabase's automated advisors reported no warnings/errors; the application-specific checks below found issues outside those advisor rules.

Production SQL ran in explicit read-only transactions. No production users, content, permissions, migrations, buckets, jobs or settings were changed. Exploit reproductions ran only in a disposable, in-memory PGlite database using the repository bootstrap manifest. Live grants, policies, constraints and function definitions were inspected to establish correspondence with those reproductions.

Prioritised findings

Priority Finding and evidence Recommended correction
1 · High / P1 A joining user can make themselves a circle moderator. Live has_column_privilege returns true for authenticated INSERT/UPDATE of circle_memberships.role. The INSERT policy checks the user's ID and public-circle/pending status, but does not require role='member'. In the isolated reproduction, a user inserted their own public-circle membership with role='moderator', passed private.circle_host(), and enabled host-only chat settings. Restrict direct membership INSERTs to the member role and revoke broad table-level INSERT/UPDATE grants before granting only intended columns. Preserve owner-only role changes through the existing validated RPC. Test direct REST attempts to assign both owner/moderator roles, including private-circle pending requests.
2 · Medium / P2 Attached chat media can be deleted after the 15-minute message window. The Storage DELETE policy treats media as unattached when its subqueries cannot see referencing messages. After the author leaves a circle, message RLS hides the reference. The isolated test deleted the Storage object for a one-hour-old message after leaving; another member could still read the message, now pointing to missing media. This is an attachment-integrity issue, not evidence of reading another member's private data. Check reference existence through a narrowly scoped internal function that can see all references, with a fixed search path and no public RPC exposure. Allow owners to discard truly unattached uploads; use authorised message deletion and the service cleanup queue for attached media. Cover leaving, blocking/unfollowing, expired deletion windows and host moderation.
3 · Medium / P2 Published-post invariants can be bypassed through direct inserts. The live check char_length(body)>0 OR id IS NOT NULL is always true because the primary key is non-null. The isolated test accepted an empty published post without media, a poll without a post_polls row, and a post timestamp 100 years in the future. The last case can distort Latest/recommendation ordering. Production currently contains none of these malformed rows. Stamp post creation time on the server and deny client assignment. Validate complete published posts, including media and poll options, at the correct transaction/publication boundary. Preserve the existing media-upload retry flow: it temporarily stores unpublished content using visibility='removed'. Do not reject legitimate media-only posts or the atomic poll RPC's intermediate insert.
4 · Medium / P2 All six starter circles have no owner. The live query returned six circles with null owner_id, including one private circle; there are also no moderator accounts. The private starter circle has no normal app user who can approve requests. Other host-only tools also lack an accountable host. Assign starter-circle ownership to an explicitly selected, real host account, creating the matching owner membership atomically. Alternatively hide/archive starter circles until hosts exist. Do not assign ownership automatically to the first registrant. Reconcile the global moderator account separately.
5 · Medium / P2 Remote migration history is not aligned with the repository. The live project records four bundled migrations. The repository has 18 timestamped SQL files, while the documented bootstrap manifest selects 13 files including setup.sql. None of the four remote version IDs matches a local filename. The documented bootstrap workaround is intentional, but standard CLI migration-history comparison/push is not ready to use directly. This is a deployment-maintenance gap, not evidence that the deployed feature schema is missing. Create and document a consistent baseline/history mapping, archive superseded migrations outside the active chain, and validate a fresh disposable deployment plus the next incremental migration. Review any history repair separately; do not reapply initial table-creation SQL to production.
6 · Medium / P2 Abandoned post uploads have no bounded retention process. The deployed cleanup jobs cover stories and community message media. The native discard action clears only local draft files. A completed post-media upload retained after cancellation/lost publishing response can remain attached to a removed draft or become orphaned. No configured job reclaims these post uploads. There are currently zero Storage objects, so no accumulated leak was observed. Distinguish abandoned uploads from deliberately soft-deleted posts, define a retention window, and queue safe post-media cleanup after a grace period. Preserve resumable uploads and published/retained content; acknowledge queue entries only after successful Storage deletion. Add bounded retries and monitoring.
7 · Medium / P2 hardening Legacy/default grants exceed client requirements. Authenticated clients retain TRUNCATE permission on 20 public tables, and anonymous TRUNCATE permission on posts was also confirmed. Default privileges grant broad table/function rights to client roles on future public objects. Existing RLS still restricts ordinary row operations. The Data API does not itself provide a TRUNCATE route, so this is excess privilege and future exposure risk, not a demonstrated anonymous HTTP table-wipe endpoint. Revoke unnecessary client table privileges and permissive future-object defaults, then explicitly grant each required operation/column. Preserve service and trigger access. Verify every app flow against the resulting permission matrix. PostgreSQL documents that TRUNCATE is outside row-level security; see the reference below.

Checks that passed

  • Schema/access: 53 public and three private app tables; RLS enabled on all 56. Anonymous/authenticated roles are not superusers and do not bypass RLS. Neither can create objects in public/private/storage schemas.
  • API boundary: a read-only Data API request for the private schema returned 406 PGRST106: Invalid schema: private. Only the two invitation-preview functions are executable by anon among the inspected app functions.
  • Functions: 102 public/private functions inspected. Every security-definer function has a fixed search path. The two public security-definer functions are service-only; private helper permissions are checked separately from schema visibility.
  • Integrity: 229 validated constraints, 143 valid/ready indexes, and no disabled app triggers. No cross-circle topic/collection inconsistencies, expired visible stories or stale live sessions were found.
  • Stories and private comments: client INSERT privileges exclude story creation/expiry timestamps; forged future story dates were rejected locally. Story expiry is constrained to creation plus 24 hours. Moving a post between circles was rejected by column permissions, and an outsider could not read its private comments in the isolated check.
  • Storage: post-media, story-media and community-media are private, with file-size/MIME restrictions. Avatars are intentionally public. No Storage objects or pending media-cleanup rows existed at the snapshot.
  • Operations: six active maintenance jobs. All recorded job outcomes in the inspected 24-hour window succeeded; 108 recorded maintenance HTTP responses were 200 without timeout. No waiting locks or idle-in-transaction sessions were observed. Autovacuum and SSL are enabled; API roles have 3-second/8-second statement timeouts.
  • Advisors: security: zero WARN/ERROR, six INFO notices for intentional deny-by-default/service-only tables. Performance: zero WARN/ERROR, 70 unused-index INFO findings. Do not drop those indexes solely on this signal: the project has no users/posts/messages and no representative workload yet.

Recovery and verification limits

The Management API reports pitr_enabled=false, walg_enabled=true and zero listed backup snapshots. A usable physical recovery window was not established from the returned metadata. This does not prove that no provider-managed backup exists. Confirm recovery coverage and perform a restore to a disposable project before launch. Supabase database backups do not include the actual Storage object files, which require a separate recovery plan.

There are zero Auth users, zero profiles/posts/comments/direct messages and six seeded circles. The database is PostgreSQL 17.11 and approximately 14 MiB. This audit establishes configuration and policy behaviour, not performance under production load, actual APNs/FCM delivery, native media capture, or a successful production Storage restore. No real-user exploit, destructive production probe, EXPLAIN ANALYZE write, cleanup invocation or backup restore was performed. Public/private app schemas and relevant Storage policies were inspected; internal provider schemas were not exhaustively audited.

Implementation order and acceptance

  1. Fix membership escalation and run negative tests for every role-management endpoint.
  2. Correct the Storage reference check and published-post validation; verify 15-minute deletion and upload/poll transaction behaviour.
  3. Define the actual hosts for starter circles and the backup/Storage recovery plan.
  4. Align migration baselines, add bounded post-upload retention and tighten legacy/default privileges.
  5. Run Auth/REST/Storage integration against a disposable Supabase stack, rerun live advisors, and test an incremental deployment plus restore. The existing app regression suite passing does not cover all of the exploit cases discovered here.
