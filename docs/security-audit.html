Findings and remediation

S01 · High · Confirmed

Joining users can grant themselves circle moderator privileges

The membership INSERT policy validates the caller and public/pending membership conditions, but does not restrict role. Live privileges allow authenticated callers to INSERT that column. A user can join a public circle with role='moderator' and satisfy private.circle_host().

Evidence: isolated test successfully inserted the role and changed host-only chat settings. This can also affect topic, prompt, collection, invitation and recognition controls that rely on the same helper. It does not grant global moderation or necessarily actual ownership: owner checks separately inspect circles.owner_id.

Fix: revoke inherited broad membership writes; explicitly grant needed columns; enforce role='member' for direct joins and private requests. Keep role assignment inside the validated owner RPC. Audit existing unexpected roles when real data exists.

Source: setup.sql:343; community_depth.sql:3.

S02 · High · Conditional purchase risk

Apple sandbox purchases use the same coin-credit path as real purchases

The deployed verifier tries Apple's production endpoint, then the sandbox endpoint. Either verified response returns a boolean that reaches the same service-only coin-credit RPC. The environment is not passed to or separated in the wallet ledger.

Impact: once store verification is configured, a valid sandbox purchase associated with an app account can credit that account's ordinary wallet without a real payment. Cryptographic verification, product matching and account binding are present; the flaw is the environment boundary.

Evidence: deployed source matches local code; the synthetic test followed the production-404/sandbox-success branch and invoked coin credit. Store Auth, signed-transaction verification and responses were mocked. No signature forgery, real transaction, configured-secret inventory or production credit was tested.

Fix: give test builds a separate backend/wallet ledger, or enforce a server-owned test-account environment allowlist with non-spendable test balances. Record store, environment and canonical transaction identity. Production wallets must reject sandbox credits regardless of client fields. Review Google test-purchase handling under the same rule.

Source: verify-coin-purchase/index.ts:83 and credit call at line 63. Apple sandbox documentation.

S03 · Medium · Confirmed missing server guard

Password confirmation for account deletion is enforced only by the screen

The client signs in again with the current password before deletion, but the deployed endpoint accepts an otherwise valid existing session and {confirmation:'DELETE'}. It does not require or validate proof of recent reauthentication.

Impact: a caller with a stolen still-valid session can bypass the screen's password step and request destructive account deletion. This is not unauthenticated deletion: the live endpoint correctly rejects missing sessions.

Evidence: a synthetic valid older session reached session revocation, profile preparation and Auth deletion without any password/fresh-auth proof. Deployed source matches. No real account was deleted.

Fix: require a server-validated, short-lived proof of reauthentication bound to this user, session and action before any deletion. Do not trust a client boolean or user metadata. Preserve global session revocation and retry-safe media cleanup.

Source: delete-account/index.ts:23; community.ts:412.

S04 · Medium · Confirmed control-flow weakness

Authentication links can replace the active account without a bound login flow

The callback accepts a caller-supplied access/refresh-token pair and calls setSession(). It also accepts token-hash sign-in links without an initiated-flow/account-switch confirmation. Exact scheme/host/path validation is good, but does not bind tokens to a login initiated on this device.

Impact: a crafted link containing an attacker's valid session can log the recipient into the attacker's account. Content entered afterward could be visible to the attacker. This is login/account-confusion risk, not proof that arbitrary invalid tokens are accepted or that the victim's existing account is stolen.

Evidence: the exact handler body accepted a synthetic foreign session and applied that user without prior flow state. Supabase validation was mocked; real invalid tokens would still be checked by Supabase.

Fix: use PKCE with a device-held verifier for app-initiated login/recovery, remove raw session injection, and handle legitimate cross-device confirmation/invitation separately. Require explicit confirmation before replacing a signed-in account. Prefer verified HTTPS app links for native delivery.

Source: App.tsx:476; supabase.ts:9. Supabase PKCE background.

S05 · Medium · Device-storage hardening

Persistent session tokens use unencrypted AsyncStorage

Supabase's entire persisted session, including refresh credentials, uses AsyncStorage. Draft messages and post drafts are also persisted without application-level encryption.

Impact: device/app-data compromise or an exposed backup may reveal reusable credentials and draft content. AsyncStorage is app-sandboxed; this is not evidence that another ordinary app or remote website can read it.

Fix: use a suitable Keychain/Keystore-backed session adapter, account for session size limits, and migrate/remove old plaintext entries. Review Android/iOS backup rules and draft encryption separately; test refresh, cold start, sign-out and account switches on devices.

Source: supabase.ts:12; React Native security guidance.

S06 · Medium · Reproduced locally

A push-token cleanup failure prevents sign-out

signOutDevice() deletes the device's push-token row before calling Auth sign-out, and throws if that cleanup fails. Storage errors can stop it even earlier. The user remains signed in when this prerequisite fails.

Evidence: an injected push-token deletion error prevented auth.signOut() from being called.

Fix: make local credential removal and UI/session/cache teardown unconditional. Attempt server revocation independently, and retain/retry failed push deregistration safely. Make device/account push ownership explicit so offline logout cannot silently expose later notifications on a shared device.

Source: community.ts:436.

S07 · Medium · Reproduced in PGlite

Leaving a circle bypasses attachment retention

The storage policy permits deleting an upload when no message reference is found. Its reference queries obey the caller's RLS. After leaving a circle, the author cannot see the old chat message, so the object incorrectly appears unattached.

Evidence: a former member deleted an attachment referenced by a one-hour-old message; another member could still read the message. This bypasses the intended 15-minute deletion window for published message attachments. The live policy matches the tested policy.

Fix: check references through a narrowly scoped internal function independent of caller row visibility, with a fixed search path and controlled invocation. Delete attached objects only through authorized message deletion and the service cleanup queue. Test leaving, blocking, unfollowing, retries and races.

Source: community_depth.sql:237.

S08 · Medium · Reproduced in PGlite

Direct post inserts bypass publication integrity and ranking safeguards

The non-empty body check is always true for rows with a primary key, and authenticated post inserts permit a chosen created_at. Direct inserts accepted an empty published post, a poll without its options row, and a post dated 100 years into the future.

Impact: malicious clients can create invalid content or distort feed ordering. This does not authorize posting to a circle where the user lacks membership. No malformed production posts exist in the captured empty dataset.

Fix: stamp timestamps on the server, grant only required columns, and validate publication atomically. Preserve media-only posts and resumable uploads; the current composer uses visibility='removed' for unfinished uploads, so a blanket non-empty-body constraint would break valid behavior.

Source: setup.sql:55 and post INSERT grant at line 829.

S09 · Medium · Privilege hardening and metadata integrity

Broad grants expose internal metadata and leave unnecessary destructive privileges

The live authenticated role has TRUNCATE privileges on 20 public tables; anonymous TRUNCATE was confirmed for posts. Default public-schema privileges also grant excessive rights to future objects. PostgreSQL TRUNCATE is outside row-level security, although the ordinary Supabase Data API has no direct TRUNCATE endpoint. This audit did not establish an anonymous HTTP table-wipe exploit.

Additional reproducible impact: report INSERT grants let a reporter supply reviewed_by, reviewed_at and resolution_note while keeping status open. The synthetic reporter impersonated another user's reviewer metadata. This does not grant actual moderation or write the protected moderation action log.

Fix: remove unneeded table/default privileges, explicitly allow required operations/columns, and make reviewer fields service/moderation-owned. Preserve trigger and service-role access. Verify with actual anon/authenticated SQL roles rather than the project owner's SQL Editor.

Source: live ACL snapshot; report policy at setup.sql:404 and line 829. PostgreSQL RLS boundaries.

S10 · Medium · Application abuse prevention

Direct content writes lack per-account rate limits and storage quotas

Circle chat has a server-enforced slow mode with locking. Equivalent per-account throttling is absent on direct-message and post creation paths. A bounded isolated test accepted 20 DMs in one transaction. Upload buckets restrict individual file size/MIME type, but do not bound a user's total uploaded bytes or object count.

Impact: an abusive authenticated account can produce excessive content, notifications or storage costs. DMs still require mutual following. This audit did not load-test production or establish the platform-wide gateway limits; a statement timeout is not a per-account abuse budget.

Fix: enforce transactional per-user/per-target limits at the database or a mandatory server boundary, including direct REST writes; add account storage budgets and bounded abandoned-upload cleanup. Keep idempotent retry behavior. Tune limits through legitimate usage rather than a single arbitrary threshold.

Source: send_direct_message at setup.sql:672; live INSERT policies and bucket configuration.

Controls that passed

  • All 53 public and three private app tables have RLS enabled. No anon/authenticated superuser or BYPASSRLS privileges; no CREATE on app/storage schemas.
  • All 57 security-definer functions have a fixed search path. Public privileged coin-credit and story-queue functions are service-only.
  • Only the intentionally public invitation preview is callable anonymously among inspected app functions. Private schema requests were rejected by the Data API with 406 / PGRST106.
  • Live account deletion, purchase and stream endpoints returned 401 without authentication. Dispatch and cleanup endpoints returned 401 with deliberately wrong scheduler secrets. Invalid invitations returned 400.
  • Live Auth public settings confirm email confirmation is required and anonymous sign-in is disabled. Sensitive Auth admin settings were not available through the current OAuth scope.
  • Isolated outsider reads of private posts and unrelated DMs returned no rows. Forged private replies, global-moderator writes, direct coin-credit calls and unauthorized role RPCs were denied. Direct wallet updates affected no rows.
  • Users cannot supply story timestamps; the 24-hour expiry constraint and insert grants held. Private post movement to a public circle was denied.
  • Post, story and community media buckets are private with size/MIME restrictions. Avatars are intentionally public. Signed URLs are bearer capabilities until expiry; do not treat them as instantly revocable by a later block or membership change.
  • Purchase code verifies signed Apple transaction claims/account binding and Google purchase state/account binding; service-only wallet credit and ledger deduplication exist. The environment flaw above remains.
  • The invitation website uses textContent for host-supplied fields and fixed, validated invitation links. The preview server binds to loopback and serves an explicit file allowlist.
  • No Supabase service key, private-key file or password URL matched the repository/history pattern scan. Public publishable keys in the invitation page are intentional, not server secrets.
  • Supabase security advisor returned zero WARN/ERROR findings and six INFO entries for intended service-only/deny-by-default tables. Automated advisors do not detect the business-logic issues above.

Fix order and acceptance checks

  1. Authorization: S01 and S09. A joining user must be unable to insert elevated roles or reviewer metadata; legitimate owners and service functions must still work.
  2. Accounts: S03–S06. A session without recent action-bound reauthentication cannot delete an account; foreign-session callbacks cannot silently switch accounts; refresh credentials use secure storage; sign-out clears local access even if cleanup fails.
  3. Payments: S02 before real purchases. Sandbox and Google test receipts must never affect real spendable balances. Test signature verification, account binding, duplicate receipts, retries and concurrent credits in a disposable environment.
  4. Content/media: S07, S08 and S10. Check outsider/member/former-member access, 15-minute boundaries, valid media-only publication, poll atomicity, concurrent limits and quota accounting.
  5. Supply chain: S11. Review advisory reachability and compatible updates; repeat lockfile audit, existing tests and native exports after changes.
