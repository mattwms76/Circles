## Planning basis and non-negotiables

This plan assumes **one focused full-stack developer** plus a limited **read-only QA/integration review** near stabilization. It uses rough effort bands to sequence work, not promises: about **7–8 focused build days** plus **1–2 review/integration days** within a nominal ten-working-day window. Parent-owned router/database/root-route assembly, operational contracts, reviewed DDL application, final checks, and source delivery are serial integration edges; they are not silently delegated or estimated as available capacity.

The approved private PostgreSQL architecture, current session/role authority, native identifiers, fixed ports, hidden scroll indicators, and removed Chats tab remain invariant. Each protected operation continues to derive identity from the session and recheck current circle/resource authorization; client account scope is cache affinity only. The evidence base is the [approved plan](../plan.md), [current TODO](../TODO.md#implement-moderation-workspace-ui-batch-1a-and-full-sprint-roadmap--23-october-2026), [selected next-batch decision](next-development-batch.md), [archived design audit](audits/design-audit-20261023.md), [dependency policy](dependency-security.md), [CI contract](continuous-integration.md), and [operations/recovery evidence](supabase-daily-operations.md).

| Planning rule | Consequence for this sprint |
| --- | --- |
| **No production fixtures or secrets** | Disposable PostgreSQL 17 and synthetic HTTP/tRPC identities prove implementation seams; no user content, reporter identity, screenshots, raw logs, or account fabrication enter artifacts. |
| **Canonical source stays Manus-managed** | Normal, parent-owned canonical/mirror delivery only after the intended tree passes checks; no Git operation, publication, signing, or restart is in this roadmap task. |
| **Evidence levels do not collapse** | Unit/component, isolated HTTP→router→service→PG, metadata/read-only checks, native/OAuth/device proof, and store/publication proof are reported separately. |
| **No scope substitution** | Existing onboarding, Circle Home, and Updates are implemented; the next community prompt is only a later product proposal, not a sprint feature. |

## Verification, release gates, and honest definition of done

### Core implementation done

A core item is implementation-done only when its scoped source, deterministic tests, isolated HTTP/router/service/PG17 tests where applicable, and exact private-schema/operations contract changes are reviewed together. For moderation this means no reporter identity exposure and race/authorization history coverage; for Batch 1A this means the measured contrast and protected-media/account-reset cases above. Parent remains responsible for router/db/root integration, migration application, exact health/recovery/security/backup contracts, final checks, and normal source delivery.

Use the existing credential-free Node **22.23.4** runtime and pnpm **9.12.0** launcher identified by the project final-check runner; do not introduce a dependency without a written compatibility/security justification. Reuse existing Vitest seams, preserve the frozen lifecycle policy, and keep E2E outside default unit discovery. Exact commands/results belong to the final parent verification record, rather than being implied by this plan.

### Release gate sequence

| Gate | Required evidence | What it does **not** establish |
| --- | --- | --- |
| **1. Local implementation** | TypeScript diagnostics/check, zero-warning lint, affected deterministic/Vitest suites, disposable PG17 and isolated HTTP tests, API build, environment/workflow validation as applicable. | Real database rows, OAuth, native UI, signing, or publication. |
| **2. Private-schema integration** | Reviewed additive SQL and legacy mapping drill; exact readiness/security/recovery/backup inventory; authorized metadata/health verification; Cron 7 and schedules unchanged. | Production fixture mutation or a safe production restore. |
| **3. Saved-source confidence** | One read-only integration review, actual exact-source CI, and actual container result before normal canonical/mirror delivery. | A dashboard checkpoint, public deployment, or store artifact. |
| **4. Launch readiness** | Approved real accounts and controlled fixtures; custom iOS/Android development/release builds; observed OAuth/logout/revocation/deep-link/SecureStore/private-circle/moderation/DM/media and two-party live tests. | Store submission unless signing/approval/build outcomes are separately observed. |
| **5. Live/public release** | Explicit release approval, signing access, verified production deployment path, relay configuration/forced-relay proof for live claims, and satisfied owner/provider/backup gates. | Continued time-dependent retention or provider guarantees without later observation. |

## Deferrals and sprint exit decision

At sprint exit, prefer a clean core handoff over broad partial UI changes: Moderator Report Workspace v1 and Batch 1A either meet their bounded evidence or remain explicitly in progress. Batch 1B is admitted only if it does not displace that handoff. All other audit families, the community prompt, four dependency exceptions, provider/gateway work, owner credential/key action, coturn, real account/custom-device testing, signing/publication, provider deletion/recovery, and time-based retention evidence stay visibly open until their specific access and evidence prerequisites are met.

No product release, production migration apply, provider configuration, account/device creation, signing, purchase, service restart, or new recurring automation is authorized by this roadmap.
