# DB-06 — Future-function EXECUTE defaults

## Finding and source status

The 2026-10-27 sanitized audit found a **future-object** risk only: `supabase_admin`, an eligible schema creator, has PostgreSQL's global `PUBLIC EXECUTE` default for future functions. It found no currently browser-executable `circles_*` function and no browser schema use. Existing routine ACLs are not changed by this remediation.

`operations/remediation/db06_future_function_privileges.sql` is deliberately a **prepared, unactivated candidate**. It makes no DDL or DML when read or handed to the normal migration workflow. It documents the only global command that can remove the observed global default and leaves that command commented until the provider and object owner approve it.

## Why a schema-only default revoke is not a fix

PostgreSQL 17 computes defaults per creating role and object type. A global `ALTER DEFAULT PRIVILEGES FOR ROLE ...` entry replaces PostgreSQL's built-in default. A matching `IN SCHEMA` entry is additive; it cannot remove a privilege supplied by the global entry. Therefore this would be misleading and is intentionally absent:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin IN SCHEMA circles_app
  REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;
```

It would not counteract global `PUBLIC EXECUTE` for functions created by `supabase_admin`.

## Provider-wide decision required

The actual correction would be the global command below, **without `IN SCHEMA`**:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin
  REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;
```

This affects every future function created by `supabase_admin`, in unrelated present/future schemas and potentially provider-managed schemas. DB-06 must not auto-apply it. Before an authorized provider change window, an approved privileged operator must:

1. Capture the exact global and schema-additive `FUNCTION` entries in `pg_default_acl` for `supabase_admin`, plus the exact eligible-creator relationships for affected schemas.
2. Confirm the provider/object-owner approves the provider-wide blast radius and supplies the intended rollback ACL. Do not assume the built-in ACL is the rollback state.
3. Inventory and isolated-rehearse provider automation/extensions that create functions as `supabase_admin`.
4. Re-run the security auditor after the change and verify the effective ACL calculation, not merely a row's existence in `pg_default_acl`.

`PUBLIC TYPE USAGE` is separate default-ACL metadata. This finding does not treat it as function execution or modify it.

## Required new private-routine pattern

While provider approval is pending, every new private routine must revoke its initial function ACL immediately after creation, using the exact routine identity (including overload arguments), then grant only reviewed callers:

```sql
CREATE OR REPLACE FUNCTION circles_app.example_private_helper(p_id uuid)
RETURNS void
LANGUAGE plpgsql
AS $$ BEGIN NULL; END $$;

REVOKE EXECUTE ON FUNCTION circles_app.example_private_helper(uuid) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION circles_app.example_private_helper(uuid)
  TO circles_app_runtime;
```

For an intentionally uncallable trigger helper, retain the `REVOKE` and omit the direct `GRANT`. Do not use `REVOKE ... ON ALL FUNCTIONS IN SCHEMA`; that could alter unrelated current provider/application routines. Do not use an unqualified function name or omit overload arguments.

## Validation boundaries

The focused Node test is credential-free and verifies the candidate's scope statements and safe template. A real PG17 drill, against synthetic roles and schemas only, remains required before any live provider-default alteration. Neither this source review nor its static test proves provider approval, future provider automation compatibility, live ACL state, browser access, per-user RLS, backup/recovery, or live rollout success.
