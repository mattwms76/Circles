# DB-11 — Compatible publish-receipt primary key

## Scope and source evidence

This prepared remediation covers only `circles_publish."postPublishReceipts"`. The sanitized catalog collected on 2026-10-27 records that it is the only audited table without a primary key, while retaining a validated non-null `UNIQUE ("actorId", "operationId")` constraint named `post_publish_receipts_actor_operation_unique`. The same catalog records validated foreign keys from `actorId` to `circles_app.users(id) ON DELETE CASCADE` and from nullable `postId` to `circles_app.posts(id) ON DELETE SET NULL`, plus the named operation-ID and payload-hash checks. RLS and forced RLS are already enabled.

The source receipt declaration is `drizzle/post-publish-receipt-schema.ts` (not `drizzle/post-publish-schema.ts`). `server/social-service.ts` uses the exact composite target in `onConflictDoNothing`, then resolves the same receipt on retry. A deleted post clears `postId` but leaves the actor/operation/payload row as a durable tombstone, preventing recreation of that operation.

The finding is a tooling/replication/design concern, not evidence of broken idempotency. No production table, receipt, account, provider, schedule, or migration history was queried or modified by this work.

## Prepared change

`operations/migrations/0022_circles_publish_receipt_primary_key.sql` is a new, unapplied, transactional migration. It applies a five-second lock timeout and thirty-second statement timeout, verifies the known receipt relation and required column shape, then verifies all of the following before changing anything:

- the validated, non-deferrable named `post_publish_receipts_actor_operation_unique` constraint still covers `("actorId", "operationId")` in that order;
- both named foreign keys retain their referenced relations and `CASCADE`/`SET NULL` delete semantics;
- both named operation-ID/payload-hash checks are still validated; and
- any already-present primary key is exactly the expected named composite key.

When no primary key is present, the migration adds `post_publish_receipts_pkey PRIMARY KEY ("actorId", "operationId")`. The post-assertion proves that this primary key and the pre-existing unique constraint use distinct backing indexes. Re-running it verifies the same post-state and does not create another constraint.

PostgreSQL cannot promote `post_publish_receipts_actor_operation_unique` with `ADD PRIMARY KEY USING INDEX`: its index is already owned by the existing named `UNIQUE` constraint. The migration deliberately retains that business constraint and permits PostgreSQL to create the additional PK-owned btree index. This preserves the named unique constraint, the exact `ON CONFLICT ("actorId", "operationId")` arbiter, both foreign keys, the check constraints, and the post-deletion tombstone behavior. The Drizzle declaration now represents both the primary key and the legacy named unique index for schema/tooling parity.

## Required isolated drill before any live decision

Use a disposable PostgreSQL 17 cluster with synthetic roles and empty synthetic `circles_app.users`/`circles_app.posts` parent tables. Load the already-reviewed receipt baseline (`0015_circles_publish_post_receipts.sql`) first, then execute `0022` once and a second time. The drill must assert from `pg_constraint`/`pg_index` that:

1. `post_publish_receipts_actor_operation_unique` remains `contype = 'u'`, valid, non-deferrable, on `actorId, operationId`;
2. `post_publish_receipts_pkey` is the sole primary key on the same ordered columns and has a different `conindid`;
3. `INSERT ... ON CONFLICT ("actorId", "operationId") DO NOTHING` still succeeds on a duplicate synthetic actor/operation pair;
4. deleting a synthetic post changes only the receipt `postId` to `NULL`, leaving the actor/operation receipt in place; and
5. deleting a synthetic user retains the established actor-cascade behavior.

Run credential-free source checks without inheriting local database or provider configuration:

```bash
env -i PATH="$PATH" HOME="$HOME" CI=1 node --test operations/tests/db11_publish_receipt_primary_key.node.mjs
env -i PATH="$PATH" HOME="$HOME" CI=1 pnpm exec tsc --noEmit
```

The focused Node test is a source-contract check; it does not execute DDL or claim a PostgreSQL drill. The PG17 drill remains a prerequisite for live activation.

## Live activation prerequisites and limits

1. Parent-approved synthetic PG17 rehearsal must pass with the receipt baseline and this new migration in order.
2. An authorized owner must confirm logical-replication/downstream consumer expectations. A primary key can change the table's default replica-identity metadata and adds a separate unique btree index; this source inspection did not inspect subscribers or provider settings.
3. An authorized operator must assess current table size/write load and approve the bounded-lock execution window. Do not increase timeouts or retry a lock/statement timeout automatically.
4. Obtain explicit live DDL approval, execute through the private migration workflow, and perform bounded post-apply catalog verification. No live DDL is authorized or performed by this candidate.
5. During parent integration, DB-14 readiness must treat either the exact validated primary key **or** the named validated `actorId`/`operationId` unique constraint as the required idempotency guarantee. That integration is intentionally outside DB-11 ownership.

`live_status`: not evaluated or activated. No claim is made about provider configuration, logical replication, downstream tooling, live data, or recovery.
