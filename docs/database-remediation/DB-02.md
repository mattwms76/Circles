# DB-02 — least-privileged application login

`operations/migrations/0017_circles_dedicated_app_login.sql` is an **unapplied** PostgreSQL 17 candidate. It creates `circles_app_login` as a disabled (`NOLOGIN`), non-inheriting, non-superuser, non-role-admin, non-database-admin, non-replication, non-BYPASSRLS role. It contains no credential material and does not enable a usable login.

The role receives only `CONNECT` to `postgres` and one explicit membership: `circles_app_runtime` with `INHERIT FALSE`, `SET TRUE`, and `ADMIN FALSE`. Thus a connection begins as the dedicated login with no inherited runtime table privileges. The existing trusted-server pool must successfully execute its already-established `SET ROLE circles_app_runtime` before an application client is returned. PostgreSQL 17 documents that `SET TRUE` permits that transition while `INHERIT FALSE` prevents automatic inheritance [1] [2]. This does not add per-user RLS; the existing API authorization model remains unchanged.

The migration is deliberately fail-closed. It requires the exact `postgres` database and the established restricted runtime role. It refuses to reuse a pre-existing `circles_app_login` role, rather than silently adapting a possibly privileged account. It also verifies that the login itself has no other membership path and that the runtime role cannot assume another role. A provider may record a separate administrator membership when a non-superuser `CREATEROLE` operator creates a role; that is operational authority, not a privilege assumed by `circles_app_login`, and must be reviewed separately.

## Runtime connection behavior

`server/_core/postgres-config.mjs` continues to accept the current pinned `postgres` direct or pooler identity until cutover. It additionally accepts only these exact dedicated identities for project `vvclcsqletcxzoaayqzq`:

- Direct: `circles_app_login@db.vvclcsqletcxzoaayqzq.supabase.co:5432/postgres`
- Session pooler: `circles_app_login.vvclcsqletcxzoaayqzq@aws-0-eu-west-1.pooler.supabase.com:5432/postgres`

Every accepted input still returns the fixed session-pooler host, port, database, CA, TLS `servername`, and hostname verifier. URL query parameters do not control the returned TLS settings. Other hosts, projects, database names, ports, and usernames are rejected. This preserves the helper’s public API and allows a protected credential switch without an app-code flag day.

## Required protected cutover

1. A parent-approved operator must rehearse the candidate on a disposable PostgreSQL 17 instance containing only a restricted `circles_app_runtime` role and an authorized role administrator. The rehearsal must cover a clean apply, the role/membership postcondition, a successful `SET ROLE circles_app_runtime`, and rejection of a pre-existing `circles_app_login` role.
2. After explicit live approval, an authorized operational credential may run the candidate migration against the pinned project. The application must not use that operational credential.
3. Through protected provider controls, separately provision a unique credential for `circles_app_login`, then explicitly enable that login. Do not place the credential in this migration, source, fixtures, or logs. Parent-owned secret distribution must change only the server-side `SUPABASE_DATABASE_URL` after the role/membership check succeeds.
4. Canary the application with the dedicated URL. Confirm, without logging credentials, that the pool initializes `circles_app_runtime`, application operations retain their expected runtime authority, and the dedicated initial session cannot use operational authority.
5. Inventory every authorized consumer of the legacy `postgres` application URL. Only after the dedicated canary and consumer migration are approved may protected operators revoke the old application credential. The separate operational credential remains independently controlled.

The candidate does not inspect provider controls, provision or revoke credentials, apply DDL, rotate any secret, or prove a live connection. The current `postgres` application connection remains source-compatible until those protected steps are complete.
