# DB-16 — Bound security-state cleanup and define retention

## Scope and source finding

This change addresses DB-16 only. The audited source at `e0e83778af66494c60dfdd0511b51b50e3d369a5` preserved one-time, hash-bound OAuth pending state, but every public OAuth start also issued an unbounded deletion of all expired pending rows. No source-visible durable `applicationSessions` purge existed.

The sanitized aggregate snapshot dated 2026-10-27 reported **0** durable application-session rows, **0** expired durable-session rows, **1** OAuth pending-state row, and **1** expired OAuth pending-state row. It contains no user/session/OAuth values. This is evidence of a lifecycle design gap, not a replay incident or storage outage.

## Source changes

`server/_core/oauth-pending-state.ts` retains a single SQL statement for cleanup plus insert, the SHA-256 fingerprints, flow-specific bindings, single-use `DELETE ... RETURNING` consume behavior, and fail-closed unavailable-store behavior. The public start path now selects and deletes at most `32` expired records in deterministic `(expires_at, state_fingerprint)` order with `FOR UPDATE SKIP LOCKED` before inserting a new state. A public OAuth start therefore cannot delete an unbounded stale backlog; locked candidates are skipped rather than waited on.

The existing ten-minute TTL is unchanged: `server/_core/oauth.ts` still defines `OAUTH_STATE_TTL_MS = 10 * 60 * 1000`, and both web and native creators still use it. Expiration continues to reject stale state independently of cleanup.

## Unactivated retention helper

`operations/remediation/db16_security_state_retention.sql` is a new **unapplied** candidate, not an installed migration or scheduled job. It is deliberately guarded: it requires the reviewed schemas, exact table columns, both existing expiry indexes, expected roles, a `postgres` installer, and an absent function of the same signature. A mismatch fails rather than replacing an unknown function.

It creates `circles_ops.run_security_state_retention(p_dry_run boolean DEFAULT true, p_batch_size integer DEFAULT 25)`. The function is `SECURITY DEFINER`, pins `search_path` to `pg_catalog`, sets a 500 ms lock timeout and 5 s statement timeout, limits each relation to 1–100 locked candidates, and uses `FOR UPDATE SKIP LOCKED`. Its only result columns are the target label, candidate count, and deletion count. It returns no row, fingerprint, OAuth value, user identifier, or app identifier. `PUBLIC`, browser roles, service role, and Circles runtime/admin roles are explicitly revoked; only `postgres` receives `EXECUTE`.

### Proposed operational horizons — approval required

These are deliberately conservative **proposals**, not approved legal, privacy, security-incident, or backup retention policy:

| State                                                | Proposed eligibility                                                | Safety boundary                                                                |
| ---------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `circles_auth.oauth_pending_states`                  | Immediately after `expires_at`                                      | OAuth state is already rejected at expiry; deletion is bounded per invocation. |
| `circles_app."applicationSessions"` expired sessions | `expiresAt` is at least 90 days old                                 | The helper has an unconditional `expiresAt <= now` predicate.                  |
| Revoked application sessions                         | `revokedAt` is at least 180 days old **and** `expiresAt` has passed | Revocation never accelerates deletion before ordinary expiry.                  |

Consequently the helper cannot delete any session record whose `expiresAt` is still in the future, whether or not it has been revoked. It does not change session creation, lookup, revocation, JWT validation, OAuth binding hashes, cookie behavior, or TTL.

## Required activation and drill prerequisites

1. Obtain explicit owner/legal/security approval for the proposed OAuth, expired-session, and revoked-session horizons. Decide whether incident hold, user-deletion, support, or jurisdictional requirements require a longer retention or no purge.
2. Use a disposable PostgreSQL 17 database with synthetic, non-production rows to apply the candidate. Verify the existing `circles_ops` schema; application-session and OAuth tables/columns; owner/index/role expectations; forced-RLS behavior under the exact `postgres` operating principal; and that browser/runtime roles cannot execute the function.
3. Drill both modes with a small batch. Confirm default dry run returns only two aggregate rows and changes no rows; confirm an explicit `p_dry_run => false` deletes no more than the configured batch per table, skips locked rows, deletes only expired OAuth rows, and never deletes a session whose `expiresAt` is in the future.
4. Review the new function against the live `circles_auth` forced-RLS contract and any exact security-auditor policy/function inventory before approval. Do not add an RLS policy merely to bypass an unexpected role mismatch.
5. After an approved live DDL installation, run protected, read-only catalog/ACL verification and record only counts and structural facts. Production deletion needs a separate explicit operational authorization after a successful dry-run review.

No production/provider connection, DDL/DML, recurring task, Cron schedule, backup change, fixture creation, service restart, or provider configuration change was performed for DB-16.

## Validation limits

The focused unit tests validate source shape and the captured query boundary. They do not prove PostgreSQL execution, live RLS/ACL behavior, provider OAuth behavior, real rate limiting, scheduled cleanup, production row deletion, or legal retention approval. A recurring retention task remains intentionally unactivated pending exact approval.
