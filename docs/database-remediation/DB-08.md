# DB-08 — Pin admin invoker helper search paths

## Scope

This source-prepared remediation covers only the two catalog-confirmed zero-argument trigger helpers:

- `circles_admin.touch_updated_at()`
- `circles_admin.reject_audit_mutation()`

The sanitized 2026-10-27 catalog records both as postgres-owned `SECURITY INVOKER` functions with no configured search path and no `anon`, `authenticated`, or `circles_app_runtime` execution. The relationship metadata records them as the helpers for the `circles_admin.operators` updated-at trigger and the immutable `circles_admin.audit` trigger respectively.

## Prepared migration

`operations/migrations/0020_circles_admin_invoker_search_paths.sql` is a new, unapplied additive migration. Within one transaction it:

1. Takes a transaction-scoped advisory lock for this exact change.
2. Fails closed unless each exact `circles_admin` zero-argument helper is a normal function returning `trigger`, is owned by `postgres`, remains `SECURITY INVOKER`, and has no existing function settings.
3. Uses only `ALTER FUNCTION ... SET search_path TO pg_catalog` for the two exact signatures.
4. Rechecks the signatures, trigger return type, owner, invoker security mode, and exact singleton configuration `search_path=pg_catalog`.

`pg_catalog` is sufficient for these helper contracts and avoids including a mutable or user-controlled schema. The migration does not use `CREATE OR REPLACE FUNCTION`, change function bodies, edit ACLs, change owners, grant browser execution, alter triggers, or rewrite migration history.

The prerequisite that `proconfig` is null is intentional: the audited source state has no explicit function settings. If a protected environment has already configured either helper, the runner must stop for review rather than silently replacing or combining an unknown setting.
