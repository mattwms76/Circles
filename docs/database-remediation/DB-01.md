# DB-01 — Restrict legacy public privacy exposures

## Status and scope

**Source status:** Prepared, unactivated candidate only. The new guarded SQL is
[`operations/remediation/db01_legacy_public_privacy.sql`](../../operations/remediation/db01_legacy_public_privacy.sql).
It is not an applied migration, has made no database connection, and must not be treated as
production/provider, Data API, backup, recovery, or per-user-RLS evidence.

**Live status:** Unchanged and unverified by this work. Live execution is blocked pending the
approval and drill prerequisites below.

The scope is intentionally limited to the three audit-confirmed UUID-era relations in `public`:
`public.circles`, `public.profiles`, and `public.follows`. They are distinct from the current
integer-keyed `circles_app` schema. No application source files are changed.

## Audited pre-state

The sanitized 2026-10-27 catalog records all three legacy relations as RLS-enabled,
not forced-RLS, and owned by `postgres`. `anon` and `circles_app_runtime` have no `SELECT`;
`authenticated` does. The candidate checks that exact relation shape, RLS/owner state, direct
read boundary, `auth.uid()` availability, policy role, permissiveness, command, predicate, and
absence of a `WITH CHECK` before changing anything.

| Relation | Exact broad `authenticated` SELECT policy | Confirmed sensitive/broad exposure |
| --- | --- | --- |
| `public.circles` | `Signed in members can discover circle listings` — `USING (true)` | Private-circle rows plus `welcome_text` and `rules` |
| `public.profiles` | `Profiles are visible to signed in members` — `USING (true)` | Other members' `interests` and `onboarding_completed_at` |
| `public.follows` | `Members see follows` — `USING (true)` | Whole authenticated follow graph |

The audit did not export rows or demonstrate a Data API leak. It also did not establish the
product contract for legacy clients. Current checked source has no reference to these three
qualified legacy tables; that does **not** prove external, retired, direct-Supabase, or unknown
client compatibility.

## Proposed narrow policy contract

After the preflight is satisfied, the candidate alters **only** those three named `SELECT`
policies. It retains table grants, all non-`SELECT` policies, the existing adjacent `auth.uid()`
semantics, owner, RLS settings, and privileged `service_role` behavior.

| Relation | Candidate `authenticated` read predicate | Intended privacy outcome |
| --- | --- | --- |
| `public.circles` | `(is_private IS FALSE) OR (owner_id = (SELECT auth.uid()))` | A signed-in member may see public legacy circles and their own private legacy circles; a non-owner cannot list a private circle. |
| `public.profiles` | `id = (SELECT auth.uid())` | A member may read only their own legacy profile, including their own onboarding fields. No cross-profile directory is asserted safe. |
| `public.follows` | `follower_id = (SELECT auth.uid())` | A member may read only follow edges they originated. Inbound/third-party graph reads are not asserted safe. |

No membership policy is inferred, and no identity mapping, lookup helper, `SECURITY DEFINER`
view, new grant, or broad revoke is created. This is deliberate: the supplied catalog does not
provide an approved mapping or a proof that every legacy private-circle member should be
recognized by RLS. If the compatibility review needs cross-profile discovery, private-circle
membership reads, or another follow-graph shape, it must specify a separate least-privilege API
or projection contract and be reviewed independently; do not weaken this candidate by guessing.

The SQL uses a session setting (`circles.db01_legacy_public_privacy_contract`) equal to
`DB01_LEGACY_PUBLIC_PRIVACY_APPROVED_V1` as an accidental-activation gate. This setting is not
a security boundary and does not substitute for approval. The executing operator must set it in
the same controlled database session only after written approval.

## Required approvals and live prerequisites

Do not apply the SQL until all of the following are recorded by the parent-controlled release
process:

1. A privacy owner approves the exact three post-state predicates above, including the retained
   access to a user's own legacy profile fields and private circles.
2. A compatibility owner inventories direct Supabase/Data API clients, legacy mobile versions,
   integrations, support/admin paths, and external consumers. They must explicitly accept loss
   of cross-profile directory reads, non-owner private-circle reads, and third-party/inbound
   follow-graph reads, or reject this candidate in favor of a separately designed narrow route.
3. A current **read-only** catalog preflight confirms the exact relation/policy/ACL facts in the
   audited pre-state. Any changed policy name, role, predicate, table shape, extra applicable
   `SELECT`/`ALL` policy, direct grant, owner, or RLS flag is a stop condition.
4. A disposable PostgreSQL 17 drill passes using synthetic roles/tables/data only. No production
   DSN, provider token, exported row, migration replay, DML, or fixture creation is authorized
   by this document.
5. The parent reviews locks/timeouts and has an approved rollback plan: preserve the current
   three `USING (true)` definitions verbatim and restore only the reviewed named policy if a
   post-activation compatibility regression is confirmed. Do not use a blanket public-schema
   policy or privilege rollback.
6. The authorized operator sets the approval setting in the same controlled session, executes
   the exact reviewed file once with stop-on-error semantics, and captures only bounded catalog
   facts. The candidate SQL itself performs no automated live activation.

## Synthetic PostgreSQL 17 drill specification

Use a fresh local/private PostgreSQL 17 cluster on loopback with inherited database/provider
variables stripped. Create only synthetic `authenticated`, `anon`, and `circles_app_runtime`
roles; an `auth.uid()` fixture that returns a transaction-local synthetic UUID; and the three
legacy tables with the exact cataloged columns, grants, RLS flags, and audited pre-policies.
Do not use real user identifiers or any provider connection.

Within a disposable transaction, enable the explicit approval setting and load the candidate.
For two synthetic subjects, test at minimum:

1. Public circles are visible to both subjects; a private circle is visible to its owner and is
   absent for the other subject.
2. A profile is visible to its matching `auth.uid()` subject only. Confirm a non-owner cannot
   observe profile rows (and therefore cannot read `interests` or `onboarding_completed_at`).
3. An outgoing follow edge is visible to its `follower_id` subject only. Confirm its followee and
   a third subject cannot observe it through the `SELECT` policy.
4. `anon` and `circles_app_runtime` remain unable to select all three tables. Existing legacy
   INSERT/UPDATE/DELETE policy behavior must be catalog-compared, not assumed from these read
   checks.
5. Preflight rejects each independently altered policy name, role, command, `USING` predicate,
   extra applicable `SELECT`/`ALL` policy, table grant, column shape, RLS flag, or omitted
   approval setting. Postflight must reject a changed narrow predicate or unexpected applicable
   read policy.

Rollback the disposable transaction and remove the fixture cluster regardless of result. A local
drill proves only synthetic PostgreSQL policy behavior; it does not prove external client,
provider-gateway, real-account, per-user identity, or recovery success.

## Credential-free source validation

Run from the DB-01 candidate only:

```sh
env -i PATH="$PATH" HOME="$HOME" CI=1 \
  node --test operations/tests/db01-legacy-public-privacy.node.mjs
```

This static contract test checks the explicit approval gate, transaction/timeouts, exact three
policy targets, audited broad prior predicate assertion, narrow post-predicates, protected
anonymous/runtime boundary, and absence of new grants/revokes, views/tables/functions/roles,
or data mutation statements. It cannot validate PostgreSQL parsing or RLS execution because no
local PostgreSQL 17 client/server is available in this candidate environment.
