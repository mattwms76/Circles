# DB-15 — Atomic direct-conversation creation

## Finding and source scope

DB-15 is a source-confirmed non-atomic write path. Before this change, `openDirect` selected or created a direct conversation and then wrote its two participant rows through the base database handle. A failure after the first participant write could therefore leave an incomplete direct conversation.

The supplied read-only relationship aggregate reported zero existing direct conversations whose participant count was not exactly two. That aggregate is historical audit evidence, not proof that the former source path was atomic and not a reason to write or repair live rows.

This remediation changes only `server/social-service.ts` at `openDirect` and adds the focused `tests/database-remediation-db15.test.ts` suite. It does not add SQL, migrate schema, change RLS, create fixtures, or modify the pending DB-14 publication-readiness seam in the same file.

## Implementation

`openDirect` retains its existing behavior:

- it rejects a self-target before looking up the database;
- it verifies that the target user exists before opening a conversation transaction;
- it keeps profile materialization outside the conversation transaction, as an independent existing profile invariant;
- it derives the direct key using numerically stable ascending user IDs;
- it uses the existing unique `conversations.directKey` conflict target and fallback read; and
- it returns `{ id }` unchanged.

The select-existing, insert-with-conflict-resolution, fallback select, and the two idempotent participant upserts now execute through one `db.transaction` callback. Participant upserts are deliberately awaited in a fixed order. If the second participant operation or any prior conversation operation fails, the database transaction rejects and must roll back the newly created conversation plus any first participant write.

The pre-existing database contract remains relevant: `conversations_direct_key_unique` makes a direct key unique, and `conversation_participants_conversation_user_unique` makes each participant upsert idempotent. No schema change is proposed by DB-15.

## Isolated validation

Run the focused suite without inherited application/provider credentials:

```bash
env -i PATH="$PATH" HOME="$HOME" CI=1 pnpm exec vitest run tests/database-remediation-db15.test.ts
```

The test calls the actual `openDirect` service with a credential-free, transaction-aware in-memory Drizzle-shaped fixture. It demonstrates these source-level behaviors:

1. Self and missing-target validation remain before a conversation transaction.
2. A fault injected immediately before the second participant upsert leaves no committed conversation and no committed participant in the fixture; a later retry creates a complete two-participant direct conversation.
3. Two overlapping calls with reversed user order are forced to read an initially absent direct key. The fixture models one unique-key winner and makes the loser wait before its fallback read; both return the same conversation ID with exactly the two canonical participants.

This is an isolated mocked-unit test. It proves `openDirect` sends the scoped sequence through the same transaction object and covers the modeled rollback/race branches. It does **not** prove PostgreSQL/Drizzle driver behavior, runtime-role authority, production transaction isolation, provider configuration, or the state of any user conversation. No production or provider connection was made.

## Parent integration: real HTTP/PG17 rollback and race proof

The A26 authority runner now includes a real HTTP→tRPC→service→local PostgreSQL17 case. A synthetic trigger raises on the second participant: the request fails and zero conversation remains. After removing the fixture-only trigger, three concurrent opens (including opposite actor direction) return one conversation with exactly two participants. The seven-test authority suite passed and removed its disposable cluster. Production authentication/token issuance is not tested: fixed synthetic users exist only in the isolated HTTP context. No production row or shipped auth path was changed.
