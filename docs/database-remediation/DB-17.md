# DB-17 — Compatible same-parent pins and live relationships

## Scope and status

This is an **unactivated source candidate** for DB-17 only. It addresses the settled invariant that a Circle can pin only a post owned by that same Circle. It does not replace application authorization: `server/social-service.ts` retains its transaction, manager check, Circle lock, and `posts.id` plus `posts.circleId` predicate before it writes a pin.

The candidate is [`operations/remediation/db17_relationship_integrity.sql`](../../operations/remediation/db17_relationship_integrity.sql). It has not been added to an applied migration registry or executed against the production database. No production connection, DDL, DML, data normalization, or migration activation occurred.

The 2026-10-27 sanitized aggregate evidence recorded zero cross-Circle pins (`pinned_post_same_circle`) and zero checked live host/Circle/stream orphans. Those point-in-time counts are not a new validation run and do not prove deployment or future state.

## Settled, deployable pin contract

The existing `circles_home_pinned_post_id_fkey` says that `circles.pinnedPostId` points to `posts.id` and clears the nullable pin when the post is deleted. That alone cannot establish that the post belongs to the Circle that carries the pin.

DB-17 prepares the following additive contract:

1. A guarded concurrent unique target over `circles_app.posts (id, "circleId")`, named `circles_posts_id_circle_id_db17_key`. `posts.id` remains the primary key; this extra ordered target exists solely because PostgreSQL foreign keys must reference a matching unique/primary key.
2. A guarded `NOT VALID` foreign key named `circles_pinned_post_same_circle_db17_fkey`:

   ```sql
   FOREIGN KEY ("pinnedPostId", id)
   REFERENCES circles_app.posts (id, "circleId")
   ON DELETE SET NULL ("pinnedPostId")
   NOT VALID
   ```

A non-null pin now requires a parent post whose `id` equals the pin and whose `circleId` equals `circles.id`. PostgreSQL also prevents moving a pinned post to another Circle (or to `NULL`) until the pin is cleared. A post delete still clears only `pinnedPostId`; it does not null or delete the Circle `id`. Clearing a pin remains valid because the nullable FK uses the normal `MATCH SIMPLE` null behavior.

The SQL verifies the expected integer columns, nullable pin column, original pointer FK shape and `ON DELETE SET NULL` action, exact concurrent-index definition, and exact composite-FK definition. It rejects a differently named compatible-looking relationship rather than silently adopting it. It uses short `lock_timeout` and bounded `statement_timeout`, needs autocommit because of `CREATE INDEX CONCURRENTLY`, and performs no row rewrite.

`NOT VALID` enforces new inserts and updates but does not itself certify every historical row. The zero aggregate count supports a separate approved validation decision; this candidate intentionally does not issue `VALIDATE CONSTRAINT`. The existing pointer FK remains DB-04’s validation concern.

## Live scalar relationship review — intentionally not executable DB-17 SQL

The source and sanitized metadata identify the following scalar relationships. No live relationship below is activated in DB-17 SQL because the documented product deletion/tombstone semantics are not yet approved. The alternatives are exact design choices to review, not instructions to run opportunistically.

| Relationship | Current source behavior and historical meaning | Approval-required exact enforcement alternative | Required decision before activation |
| --- | --- | --- | --- |
| `streams.hostId → users.id` | A stream is host-owned and `streams` remains queryable after `status` becomes `ended`; the source does not delete it on `end`. | `FOREIGN KEY ("hostId") REFERENCES circles_app.users(id) ON DELETE RESTRICT NOT VALID` preserves host attribution but blocks physical user deletion. A tombstone/retained-user model would be needed instead if user purge is required. | Whether user identities are tombstoned/retained for historical streams, or whether physical user deletion is supported. |
| `streams.circleId → circles.id` | The reference is nullable. Streams may be Circle-scoped, and ended streams are retained. | `FOREIGN KEY ("circleId") REFERENCES circles_app.circles(id) ON DELETE SET NULL NOT VALID` preserves the ended stream while removing a deleted Circle link. | Whether a deleted Circle must leave a detached historical stream, a Circle tombstone link, or cause different retention. |
| `activeHostLeases.hostId → users.id` | One lock/lease row per host; it is mutable operational state, not stream history. | `FOREIGN KEY ("hostId") REFERENCES circles_app.users(id) ON DELETE CASCADE NOT VALID` is only appropriate if the approved user lifecycle permits removal of this operational lease. | Exact user deletion/tombstone behavior and whether a lease may be removed during user deprovisioning. |
| `activeHostLeases.streamId → streams.id` | The nullable pointer is set only for a current active host stream and is cleared when the stream ends. | `FOREIGN KEY ("streamId") REFERENCES circles_app.streams(id) ON DELETE SET NULL NOT VALID`. | Confirm stream rows are never physically removed before clearing current leases, or approve this defensive clear. |
| `liveViewers.streamId → streams.id` | Viewer rows are durable presence/history (`leftAt` distinguishes departure); ended streams remain queryable. | `FOREIGN KEY ("streamId") REFERENCES circles_app.streams(id) ON DELETE RESTRICT NOT VALID` preserves viewer history but can block stream deletion. | Stream/viewer retention, archival, and physical-delete policy. |
| `liveSignals.streamId → streams.id` | Signals are transient: the end path deletes them and expiry cleanup deletes bounded old rows. | `FOREIGN KEY ("streamId") REFERENCES circles_app.streams(id) ON DELETE CASCADE NOT VALID` is safe only after confirming that a physically deleted stream may also delete all remaining signals. | Signal retention and any administrative/export requirements. |
| `liveChat.streamId → streams.id` | Chat is persisted and read by active participants; it is not deleted when a stream ends. | `FOREIGN KEY ("streamId") REFERENCES circles_app.streams(id) ON DELETE RESTRICT NOT VALID` preserves chat but can block stream deletion. A nullable archive target would require a separately designed schema change. | Chat retention/export policy and whether physical stream deletion is allowed. |

The table distinguishes transient signal cleanup from ended-stream, viewer, and chat history. No `CASCADE` or `RESTRICT` action for these live relationships appears in the DB-17 executable candidate. This keeps residual product choices open rather than silently deleting history or breaking a future deletion workflow.

## Required isolated PostgreSQL 17 drill before any approval

Run only in a disposable loopback PostgreSQL 17 cluster with synthetic rows and a controlled environment; do not use a provider, production URL, real account, or copied data. Apply the project baseline and `0008_circles_home.sql` in their normal prerequisite order, then execute the DB-17 candidate in **autocommit** mode.

The drill must show all of the following:

1. A Circle can pin its own post; clearing the pin succeeds.
2. Pinning a post from another Circle fails with foreign-key SQLSTATE `23503`.
3. Reparenting or nulling a pinned post’s `circleId` fails with SQLSTATE `23503` until the pin is cleared.
4. Deleting a pinned post leaves the Circle row intact and changes only `pinnedPostId` to `NULL`.
5. Re-running the candidate accepts the exact post-state, while a same-name mismatched index/constraint fails closed.
6. The audit queries for cross-Circle pins and live host/Circle/stream orphans are re-run as aggregate-only checks immediately before a live decision.
7. Each approved live alternative is drilled with its chosen delete/tombstone scenario; do not infer its safety from the pin drill.
