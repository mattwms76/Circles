# DB-14 — Critical feature database readiness

## Scope and source status

DB-14 extends source-level, fail-closed database readiness. It owns the exact catalog contracts in `server/_core/database-contracts.ts`, the backend readiness gate, email identity readiness probe, the prepared operations companion, and the protected composer’s status seam. It does **not** apply DDL, contact a provider, change schedules, start a service, inspect credentials, or publish a migration.

The composer API remains `Promise<{ ready: boolean }>` at `server/social-service.ts#getPostPublicationStatus`. Its body now delegates to the stricter DB-14 catalog helper only; DB-15 publication/idempotency transactions are unchanged.

## Runtime contracts

All three SQL probes use bounded `LIMIT 1` catalog/privilege aggregates. They read no application rows, receipt contents, identity values, hosts, or credentials.

`DATABASE_READINESS_SQL` preserves the restricted `circles_app_runtime` and 27 readable RLS-enabled app-table gate, then requires:

- source-accurate social integrity columns/types, including the exact quoted `circles_app."socialUploads"` regclass and PostgreSQL catalog `int2[]` constraint-key casts;
- source-named message/conversation/participant constraints, valid FKs and uniqueness indexes, and the partial message idempotency index;
- the enabled deferred-immediate message-author trigger, owner, invoker mode, fixed path, source-owned body MD5, no runtime execute privilege, and no public execute ACL;
- exact runtime and restrictive browser-denial message policy shapes.

Readiness remains `{ ok, database, oauthState, liveRelay }` while email auth is disabled. When enabled it additionally exposes the pre-existing `emailAuth` boolean. A critical catalog mismatch makes `database` false; no readiness path mutates data.

`EMAIL_IDENTITY_READINESS_SQL` is queried only by the optional identity store. It requires the exact `circles_identity.provider_links` table/RLS/columns/constraints/grants/policies and fails closed for absence or drift. It is not proof of provider settings, identities, login, native behavior, or account-level E2E flow.

`POST_PUBLICATION_STATUS_SQL` is the protected composer preflight. It verifies the exact receipt schema, grants/RLS/policies, named baseline `post_publish_receipts_actor_operation_unique`, validated FKs/checks, and an exact actor-operation PK-or-UNIQUE guarantee. It does not mutate or read publication content.

## Prepared operations companion

`operations/remediation/db14_integrity_health.sql` is additive and unactivated. Within its single transaction it sets `lock_timeout` to 2 seconds and `statement_timeout` to 15 seconds, takes the DB-14 advisory lock, and refuses to run if **any** `circles_ops.run_daily_critical_feature_health` overload already exists. It uses `CREATE FUNCTION`, never `CREATE OR REPLACE`, so a prior `SECURITY DEFINER` signature cannot carry ACL state forward.

Before commit, its postflight requires the exact zero-argument function to be postgres-owned, `SECURITY DEFINER`, fixed at `search_path=pg_catalog`, explicitly executable only by postgres, without `PUBLIC`, unexpected grantees, or grant options. The function returns only `healthy` and a fixed sanitized `error_code`; it creates no Cron job and preserves the existing daily health definition/history/schedule.

If identity storage is installed, the operations health function also validates its private catalog contract. It deliberately does not activate email auth or certify a provider/native/account flow.

## Disposable PostgreSQL 17 proof

The opt-in drill at `operations/tests/db14-critical-contracts.pg17.py` was run successfully with:

```bash
CIRCLES_DB14_LOCAL_PG17=1 /usr/bin/python3 -B operations/tests/db14-critical-contracts.pg17.py
```

It created a unique loopback-only PostgreSQL 17.11 cluster, applied 16 source migrations through `0014_circles_email_identity.sql` and `0015_circles_publish_post_receipts.sql`, and added only the separately source-owned restrictive browser-denial policy needed by the messages readiness contract. It then executed the exact exported runtime SQL as `circles_app_runtime` and the prepared health function as postgres.

The drill verified actual PG17 FK names and the trigger-body MD5, rejected folded `circles_app.socialUploads` while accepting the quoted mixed-case relation, and passed the healthy contract. It then demonstrated fail-closed behavior for a dropped column, dropped idempotency index, missing runtime policy, public trigger-helper execute grant, and an existing malicious prior health-function signature. The cluster and synthetic database were removed in `finally` cleanup. It accepts no DSN or `.env` input and has no production/provider path.

## Required live prerequisites

1. Obtain explicit authorization and compare the exact protected target role/policy/ACL inventory immediately before any DB-14 application.
2. Apply `db14_integrity_health.sql` once through the approved private PostgreSQL workflow. A pre-existing health function/overload is a stop-and-review condition, not a replacement path.
3. Only after approved application, invoke the companion from the existing trusted daily operations workflow. Do not create or alter a schedule automatically.
4. If email auth is enabled, separately authorize provider configuration and real-account validation.

The local fixture is isolated execution evidence, not a production migration, provider, backup/recovery, native, or account-level proof.
