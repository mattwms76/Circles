# DB-03 — Harden the trusted-server authorization boundary

## Finding and retained architecture

The DB-03 audit finding is an intentional, defense-in-depth limitation: the
`circles_app_runtime` policies use `USING true` / `WITH CHECK true` for the
trusted API runtime. The database role isolates browser and non-application
roles; per-account and per-Circle authorization remains mandatory API/service
logic. The supplied catalog evidence identifies `circles_app_runtime` as
NOLOGIN, non-superuser, non-BYPASSRLS, with private-schema access only where
required by the application.

This remediation does **not** claim per-user RLS, account-scoped SQL policy,
or a live authorization proof. Broad runtime predicates remain an architectural
choice. Introducing actor-scoped helpers or transaction-local end-user RLS
would require a separately designed actor/guest/admin transaction model and
an audit of every existing query contract.

## Runtime-pool controls

`server/runtime-role-pool.ts` now applies these controls for every checkout:

1. It executes `SET ROLE circles_app_runtime` and, before exposing the
   connection, runs a bounded catalog check that requires `current_user` to be
   that exact role and requires it to be NOLOGIN, NOINHERIT, non-superuser,
   non-BYPASSRLS, with no parent-role memberships.
2. A failed role change or verification destroys the client and returns only
   `RuntimeRoleInitializationError`; the client is never handed back to the
   pool as the login principal.
3. Inspectable node-postgres text/config query forms are lexed before
   submission. The lexer skips PostgreSQL nested block comments, line comments,
   ordinary strings, `E`/unicode escape strings, quoted identifiers, and
   dollar-quoted bodies. It rejects executable `SET ROLE`, session
   authorization changes (including `session_authorization` spelling),
   `RESET ROLE`, `RESET ALL`, `DISCARD`, and executable `set_config(...)`
   calls. Consequently, a harmless literal such as
   `SELECT '; SET ROLE postgres' AS note` is delegated normally rather than
   rejected. Promise and callback forms retain their normal error shape;
   uninspectable low-level `Submittable` objects are rejected. The internal
   driver `connection` property is not exposed through the guarded view.
4. Calling `PoolClient.release()` makes the guarded checkout terminal
   immediately. The raw node-postgres client is **not** returned at that point:
   the proxy performs bounded raw `DISCARD ALL` cleanup outside application
   code and only then returns it to the pool. A cleanup timeout, driver/query
   error, or leaked transaction (for which `DISCARD ALL` is invalid) destroys
   the raw client. Queries submitted through that proxy after `release()` fail
   with `RuntimeRoleClientReleasedError` rather than racing the cleanup.
   Explicit `release(error)` preserves node-postgres destruction semantics.

The lexical guard and cleanup barrier are accidental-misuse controls for the
trusted server codebase, **not** a sandbox against hostile code running in the
same process. They do not eliminate the authority of the underlying login
identity. DB-02's separate dedicated-login provisioning and approved
credential cutover remain necessary to reduce that residual trust.

## Validation

### Source-equivalent tests

`tests/database-remediation-db03.test.ts` uses mocked node-postgres clients to
verify:

- checkout requires both `SET ROLE` and restricted-role verification;
- unsafe verification destroys the checkout;
- lexical recognition accepts strings, E strings, quoted identifiers,
  dollar-quoted bodies, and nested comments containing control-looking text;
- executable role/session/reset/discard/set-config paths are rejected before
  the driver receives them, including a query-config callback;
- successful release issues `DISCARD ALL`, makes the proxy terminal, and only
  then releases the raw client; and
- cleanup query failure, timeout, and explicit release-error paths destroy as
  required.

`tests/schema-connection.test.ts` retains the runtime checkout smoke coverage
alongside the connection and private-schema checks.

Run without inherited provider credentials:

```sh
env -i PATH="$PATH" HOME="$HOME" CI=1 pnpm vitest run tests/database-remediation-db03.test.ts tests/schema-connection.test.ts
env -i PATH="$PATH" HOME="$HOME" CI=1 pnpm check
```

### Executed disposable PostgreSQL 17 drill

`operations/tests/db03-runtime-pool.pg17.mjs` is an opt-in real-pool drill. It
has no DSN argument, does not read `.env`, has no provider/production
connection path, and starts a unique temporary PostgreSQL 17 cluster bound
only to `127.0.0.1`. Its spawned database processes receive a fixed minimal
allowlist environment. It creates only synthetic `db03_synthetic_login` and
`circles_app_runtime` roles, then removes the cluster in `finally`.

The executed command was:

```sh
env -i PATH="$PATH" HOME="$HOME" CI=1 CIRCLES_DB03_LOCAL_PG17=1 pnpm tsx operations/tests/db03-runtime-pool.pg17.mjs
```

The drill passed these assertions against PostgreSQL 17.11:

- `pool.query()` promise, config, pool callback, and `connect(callback)` paths
  all observe `current_user = circles_app_runtime`;
- a real direct `SET ROLE postgres` is rejected while the current user remains
  the runtime role;
- control-looking ordinary/E/dollar literals, a quoted identifier, and nested
  comments execute normally;
- a normal `BEGIN`/`COMMIT` transaction remains usable;
- release clears a persistent `application_name` GUC and a named prepared
  statement before the same backend is checked out again, while a
  post-release query fails immediately;
- a leaked transaction makes `DISCARD ALL` fail, destroys that backend, and
  yields a replacement checkout under the runtime role; and
- terminating the backend before its cleanup produces an out-of-transaction
  cleanup-driver failure, destroys it, and yields a safe replacement checkout.

This is a synthetic local runtime-pool proof only. It does not connect to a
provider, create production roles or data, run a production migration, or
prove API resource authorization.

## Live rollout prerequisites and status

No production/provider connection, DDL, DML, migration, credential action, or
service restart was performed. This is an unactivated candidate-source change.

Before an authorized rollout, a parent/operator must:

1. integrate and review this candidate against the final DB-02 connection
   configuration and any future direct `PoolClient` consumers;
2. execute the credential-free source checks, then an authorized isolated
   session-pool drill with the target runtime/login relationship;
3. confirm the live `circles_app_runtime` role still has the exact restricted
   attributes asserted by this candidate and that its login principal may set
   that role;
4. separately provision and approve the DB-02 dedicated application login,
   credential distribution, authorized-consumer cutover, and old-credential
   revocation; and
5. retain mandatory API authorization tests. Any desired per-user RLS requires
   separate transaction/actor architecture approval rather than unused helper
   code in this patch.
