# DB-13 — Verify provider API schema exposure without guessing

## Purpose

`DB-13` adds `scripts/verify-database-gateway-exposure.mjs`, a read-only verifier for the Data API/PostgREST exposure boundary of Supabase project `vvclcsqletcxzoaayqzq`. It does not modify database settings, schemas, grants, policies, provider configuration, or application code.

The prior catalog audit correctly remains **UNKNOWN**. Its session and `pg_db_role_setting` checks had no `pgrst.db_schemas` value, which is not proof that `circles_app` or another `circles_*` schema is absent from the provider gateway. The parent-owned provider read on 2026-10-27 likewise returned no catalog setting rows; it remains catalog evidence only.

## Evidence contract

The verifier accepts exactly one input mode:

- `--management-api` makes one bounded, read-only `GET` to the documented, project-pinned Supabase Management API PostgREST configuration endpoint. It reads a protected token only from `CIRCLES_SUPABASE_MANAGEMENT_API_TOKEN`; it never accepts a token, URL, header, or project reference on the command line.
- `--settings-file <path>` reads a reviewed, owner-supplied evidence envelope. This is the required mode for a complete PASS/FAIL result because the documented Management API PostgREST response does not attest the Dashboard's **Automatically expose new tables** setting.

The evidence file is not a provider credential dump. It must be an owner-controlled private file with this exact shape. The listed values below are illustrative, not a claim about the live project.

```json
{
  "evidence_version": 1,
  "provenance": {
    "provider": "supabase",
    "source": "supabase_management_api_and_dashboard",
    "project_ref": "vvclcsqletcxzoaayqzq",
    "observed_at": "2026-10-27T12:00:00.000Z",
    "reviewed": true
  },
  "postgrest": {
    "db_schema": "public,graphql_public",
    "max_rows": 1000,
    "db_extra_search_path": "public,extensions",
    "db_pool": 20,
    "db_pool_acquisition_timeout": 10
  },
  "auto_expose_new_tables": false
}
```

The checker requires all five documented PostgREST response fields with bounded scalar types. It permits extra provider fields but ignores and never reports them. The provenance must be a reviewed Supabase Management API, Dashboard Data API settings, or combined capture for the pinned project and an ISO timestamp. A wrong project, malformed response, missing automatic-exposure Boolean, unreviewed capture, unavailable token, network failure, or response larger than 64 KiB produces **UNKNOWN** and a nonzero exit code.

## Result interpretation

A full **PASS** requires a valid reviewed evidence envelope, no schema whose name starts with `circles_` in the exposed schema list, and `auto_expose_new_tables: false`.

A **FAIL** is emitted if any `circles_*` schema is exposed. It is also emitted if automatic exposure for new tables is enabled, because the private-schema contract requires explicit review before Data API privileges are granted to future objects. This result does not claim that enabled automatic exposure alone proves an existing `circles_*` Data API route.

A direct Management API response can still produce a useful **FAIL** when it names `circles_*`. If it names no such schema, the result remains **UNKNOWN** until the auto-exposure setting is independently included in reviewed evidence. Absence of a database `pgrst.db_schemas` setting is also **UNKNOWN**, never PASS.

The report contains only the pinned project reference, schema names, bounded statuses, and required field names. It never prints access tokens, request URLs, headers, raw settings, raw errors, or SQL results.

## Approved invocation

Run the focused unit test without inherited credentials:

```bash
env -i PATH="$PATH" HOME="$HOME" CI=1 \
  node --test operations/tests/database-gateway-exposure.node.mjs
```

For an authorized review, the parent/operator must create the envelope in an owner-controlled private location and run:

```bash
env -i PATH="$PATH" HOME="$HOME" CI=1 \
  node scripts/verify-database-gateway-exposure.mjs \
  --settings-file /private/circles/DB-13-provider-settings.json
```

An authorized parent may use `--management-api` only through a protected credential-injection mechanism. This unit neither discovers credentials nor performs that request. It does not use a browser, login flow, SQL connection, DDL/DML, provider write, migration, fixture, service, or schedule.

## Remaining prerequisite

A current authorized provider settings capture must record the pinned project’s exposed schemas and automatic-exposure setting, meet the envelope contract, and be reviewed by the designated owner. Database role denials and the empty catalog setting result remain important defense-in-depth evidence, but neither certifies the provider gateway setting.
