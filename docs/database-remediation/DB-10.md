# DB-10 — Workload-aware index review

## Finding and source status

The 2026-10-27 sanitized catalog snapshot recorded **98 nonunique indexes with `idx_scan = 0`** among 240 scoped indexes. This is a workload-dependent observation, not an error condition and not evidence that any one index is redundant.

The snapshot's database statistics reset was `2026-10-02T17:54:14.043Z`; the catalog collection was at `2026-10-27T11:37:31.460Z`. The observed interval was 2,137,397.417 seconds (about 24.738 days). That interval may omit rare, seasonal, administrative, recovery, or future paths, and a statistics reset makes it explicitly non-lifetime evidence.

`scripts/review-database-index-workload.mjs` is prepared source-only review tooling. It has not connected to, changed, or certified any live database.

## What the reviewer does

The reviewer dynamically loads the established `server/_core/postgres-config.mjs` helper. It accepts no DSN, host, port, database-user, or password flag, so the existing pinned project/host/CA validation remains the connection authority.

Within one `BEGIN TRANSACTION READ ONLY` transaction it:

1. Sets finite transaction-local statement and lock timeouts.
2. Reads only `pg_stat_database`, `pg_index`, `pg_class`, `pg_namespace`, `pg_stat_user_indexes`, and `pg_constraint` metadata for the audited Circles schemas: `circles_admin`, `circles_app`, `circles_auth`, `circles_ops`, `circles_publish`, `private`, and `public`.
3. Produces a bounded sample of at most 250 nonunique, nonprimary zero-scan observations.
4. Annotates each observation when it backs a catalog constraint or covers a foreign-key child-column prefix.
5. Writes a new mode-`0600` JSON report with safe identifiers and aggregate counters only. It intentionally omits index definitions, query text, database identity, connection values, and application rows.

Every observation is emitted with the explicit disposition `retain_pending_workload_and_plan_review`. The report uses `review_only` even when catalog evidence is complete; it never treats zero scans as a pass/fail deletion threshold. Missing, malformed, or truncated metadata changes the report to `review_only_incomplete_catalog_evidence`, not to an automatic action.

The tool contains no `DROP INDEX`, DDL, or DML path. It does not generate migration SQL and does not execute a removal action.

## Interpretation and required review

`idx_scan` is cumulative since the statistics reset. It does not prove that an index was never needed, will never be needed, or is unused by all internal work. In particular, reviewers must consider:

- the reset window and whether it spans representative product, maintenance, release, and incident-recovery cycles;
- rare, seasonal, administrative, support, export, and future product workloads;
- planner choices and parameter/cardinality-sensitive alternatives using authorized isolated plan evidence;
- unique, primary, exclusion, and other constraint-backed indexes; and
- foreign-key child-side support, including the fact that referential work can be operationally important even if the snapshot is not representative.

Before a separately proposed schema change, an authorized reviewer must map the exact index to workload telemetry, collect isolated plan evidence without exporting application rows, check constraint and foreign-key compatibility, assess lock/rollback behavior, and submit a distinct approved migration. DB-10 neither authorizes nor prepares that migration.

## Authorized operational use

Use only from an approved secure server context where the established connection helper can obtain its existing protected configuration. Do not paste a credential into a command line, add an environment file, or add a connection override. Choose a new, private output destination outside source control.

```sh
node scripts/review-database-index-workload.mjs \
  --project-dir /home/ubuntu/circles \
  --json-output /private/authorized-output/db10-index-workload.json
```

The command performs read-only catalog/statistics collection only. A successful file write is not workload proof, a query-plan review, a production index change, or a backup/provider/RLS certification.

## Credential-free validation

The focused test uses a mocked catalog client; it cannot connect to a database and has no production fixture:

```sh
env -i PATH="$PATH" HOME="$HOME" CI=1 \
  node --test operations/tests/database-index-workload.node.mjs
```

The test verifies the read-only transaction contract, finite observation limit, statistics-reset interpretation, constraint/FK annotation, identifier redaction, absent destructive SQL, rejection of arbitrary connection arguments, and rollback on a catalog-query failure.

## Live status and prerequisites

Live review remains pending parent approval and protected operational access. Prerequisites are:

1. An authorized operator and secure runtime context with the existing pinned connection configuration available through the approved mechanism.
2. Confirmation that catalog/statistics access is permitted and that the output destination is private and new.
3. Review of the report's reset window against representative workload coverage.
4. Separate plan/workload evidence and explicit change approval for any future index proposal.

No production connection, query-plan capture, DDL, DML, migration replay, index removal, schedule, provider change, or backup/recovery assertion was performed for DB-10.
