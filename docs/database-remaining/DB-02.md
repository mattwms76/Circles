# DB-02 — protected least-privileged application-login cutover

## Status and scope

The audited live state is preserved by this candidate: `circles_app_login` is a detached `NOLOGIN`, `NOINHERIT`, non-superuser role; `circles_app_runtime` remains the non-login, non-inheriting runtime authority. No migration is applied by this work, no credential is generated, and no production connection, provider control, service restart, or secret-store change is performed.

`operations/migrations/0017_circles_dedicated_app_login.sql` remains an unapplied historical candidate and must not be rerun against the already-existing live role. The observed approved state has only the provider-owned incoming `postgres → circles_app_login` administration edge; it has no app-login-to-runtime edge while detached. The new artifacts prepare an operator-controlled activation rehearsal that adds the SET-only edge atomically, and a reversal that removes it. They do **not** change the approved 43-table private inventory, current 9 admin tables, routines, policies, grants, sessions, rows, keys, or schedules.

A configuration mode is not treated as proof of safety. In dedicated mode, `server/_core/postgres-config.mjs` requires an actual URI whose principal is the exact dedicated role; the DB-02 runner then connects and proves `session_user`, `current_user`, `current_database`, direct-denial, runtime-role transition, and required helper grants.

## Actual source consumers and separation

The only application runtime constructor is `server/db.ts`, which gets its pool options from `server/_core/postgres-config.mjs` and hands them to the existing `RuntimeRolePool`. DB-02 does not modify that pool or the application services; it continues to run its existing `SET ROLE circles_app_runtime` initialization before handing a client to queries.

Source-visible **operations** consumers of the shared config helper are `scripts/circles-supabase-security-audit.mjs`, `scripts/circles-oauth-security-audit.mjs`, `scripts/migrate-to-supabase.mjs`, `scripts/recover-api.mjs`, `scripts/recovery-continuity.mjs`, and `scripts/review-database-index-workload.mjs`. The email HTTP/identity runners use their own disposable local fixtures. These consumers must be explicitly classified and supplied only the protected operational URI; they must not inherit the dedicated app URI merely because it exists in another secret scope.

## Catalog preflight and role contract

`operations/remediation/remaining_db02_preflight.sql` is read-only and transaction bounded. It locks a DB-02 advisory key and refuses unless all of the following are true:

- Database is exactly `postgres`; the six reviewed private schemas exist.
- `circles_app_login` is still detached (`NOLOGIN`, `NOINHERIT`, no superuser/create-db/create-role/replication/BYPASSRLS/config/connection-limit authority).
- `circles_app_runtime` retains equivalent restricted flags and has no upward membership path.
- The detached login has **no** outgoing membership. It has exactly the observed provider-owned incoming `postgres` administration edge (`ADMIN TRUE`, `INHERIT FALSE`, `SET FALSE`); that edge does not give the app login authority. Activation adds the sole outgoing `circles_app_runtime` edge with `ADMIN FALSE`, `INHERIT FALSE`, and `SET TRUE`.
- The login has database `CONNECT`, no database `CREATE`, no private-schema `USAGE`/`CREATE`, and no direct schema/relation/column/routine ACL.
- The reviewed private relation inventory remains exactly 43 tables across `circles_admin`, `circles_app`, `circles_auth`, `circles_identity`, and `circles_publish`.
- Runtime schema access and current application/helper grants remain present: app users, OAuth pending state, identity links, publishing/receipt helpers, and the narrow admin settings routine. Runtime `TRUNCATE` remains absent from all application/helper tables.

The activation SQL repeats these checks in the same transaction immediately before its only mutations: creating the sole SET-only `circles_app_login → circles_app_runtime` edge and `ALTER ROLE circles_app_login LOGIN`; it then confirms no other login-role flag changed. The rollback SQL requires that exact active boundary, refuses while any dedicated-login session remains, revokes the SET-only edge, and changes `LOGIN` back to `NOLOGIN`.

## Parent-owned, reversible cutover sequence

These are instructions for a separately authorized parent/operator. This candidate does not execute them.

1. **Freeze scope and inventory.** Record the current secret consumers and runtime revision. Confirm the current app is still legacy mode, `circles_app_login` remains `NOLOGIN`, and the operational URI is not present in the intended dedicated app environment. Do not rotate `postgres`, JWT, media, or any unrelated secret.
2. **Run protected read-only preflight.** Inject only the operational `SUPABASE_DATABASE_URL`, `CIRCLES_DB02_ACTION=preflight`, and the intentional-action guard into an isolated operator process. Run `node scripts/remaining-db02-cutover.mjs`. A pass changes no role state; a failure means stop and investigate catalog drift without force-normalizing grants.
3. **Supply only the new app password in its protected URI.** The owner chooses one unique password and constructs `CIRCLES_APP_DATABASE_URL` only in protected operator input at the exact dedicated pooler identity. With action `activate-temporary`, the runner parses that URI in memory, rejects reuse of the operational password, and parameterizes the value into a transaction-local server setting before safely applying it to the fixed `circles_app_login` identifier. It never prints, writes, returns, or stores the URI/password. Do not use the old `postgres` password, echo a URI, create a password artifact, or treat password provisioning as a cutover.
4. **Temporary activation plus real connection verification.** In an isolated operator process with the operational URI and the one app URI supplied through protected input, run action `activate-temporary`. It provisions only that owner-chosen dedicated password, performs atomic catalog checks, enables only `LOGIN`, then makes a real TLS connection as the dedicated principal and verifies the limited direct session plus `SET ROLE circles_app_runtime`. If this verification fails, the runner attempts the protected `NOLOGIN` rollback before returning a redacted failure.
5. **Canary the app with isolated credentials.** Parent injects only `CIRCLES_DB_LOGIN_MODE=dedicated` and `CIRCLES_APP_DATABASE_URL` into a narrowly scoped app canary. It removes `SUPABASE_DATABASE_URL` from that app process; configuration rejects any co-residence. Parent verifies normal API/readiness behavior and the existing pool’s runtime-role initialization. Do not run direct destructive privilege probes against production.
6. **Migrate and verify every consumer.** Keep the operational URI only in explicit reviewed operator contexts listed above. Confirm the app canary, background/operator consumers, backup/recovery/audit paths, secret scopes, deployment manifests, and rollback holder are all classified. Do not silently reuse the app URL for operations or the old privileged URI for the dedicated app.
7. **Complete/hold the operational credential boundary.** Once the dedicated app deployment is verified, remove the old `SUPABASE_DATABASE_URL` only from application deployments. Preserve it in the parent-controlled operational scope until every legitimate operational consumer has a separately approved replacement/retirement plan. Never blindly delete or globally rotate the original `postgres` credential; DB-02 is not authorization to do so.
8. **Rollback if required.** First restore a verified legacy app process that contains only the operational `SUPABASE_DATABASE_URL` and no `CIRCLES_APP_DATABASE_URL`, then drain/close dedicated app connections. Run action `rollback-detached`. The SQL refuses if a `circles_app_login` session remains. The unique dedicated password remains protected for a later reviewed retry, while the role returns to the currently approved detached `NOLOGIN` state **without** a runtime membership edge.
