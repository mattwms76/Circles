# DB-03 — Validated actor transaction scope and scoped runtime RLS

## Status

**Candidate implementation only; production activation is not ready.** No production or provider connection, DDL/DML, credential change, service restart, publication, browser action, or real-account fixture was performed.

This candidate replaces selected permissive `circles_app_runtime` policies with real actor/resource predicates in `operations/remediation/remaining_db03_actor_rls.sql`. The SQL is deliberately not in the automatic migration chain. It refuses to execute unless the owner runs it in a reviewed transaction with:

```sql
SET LOCAL circles.db03_actor_rls_contract = 'DB03_ACTOR_RLS_APPROVED_V1';
```

The gate is an activation control, not the enforcement mechanism: the candidate contains 72 concrete policies and the PG17 drill applies them and observes cross-actor RLS refusals.

## Actual request-to-database path

For real `/api/trpc` HTTP calls, the actor path is:

1. `server/_core/context.ts` calls the existing `sdk.authenticateRequest(req)`, which verifies the signed durable session and obtains the current source user.
2. `databaseActorFromAuthenticatedUser` accepts only a positive safe-integer source user ID, a verified scheduler identity, or guest. A malformed authenticated principal becomes no user/guest; it is never converted from a viewer/input ID.
3. `server/_core/trpc.ts` puts every `publicProcedure`, `protectedProcedure`, and `adminProcedure` request carrying that marker into `withDatabaseActorTransaction` **before** service code runs.
4. `server/db.ts` opens one outer Drizzle transaction, runs only server-derived `SET LOCAL circles.actor_id` and `SET LOCAL circles.actor_kind`, then binds that transaction in `AsyncLocalStorage`.
5. `getDb()` returns that already-scoped transaction to the existing service layer. Existing `db.transaction(...)` calls therefore become nested savepoints and retain their present parent-lock/transaction order.
6. Commit/rollback clears the local settings. The existing `RuntimeRolePool` still performs bounded `DISCARD ALL` before returning a checked-out connection; leaked transactions are destroyed rather than reused.

`viewerScope` and similar request fields remain affinity checks in routers only. They do not enter PostgreSQL settings and cannot become database authority.

The optional `databaseActor` context property exists solely to leave existing `router.createCaller` unit fixtures database-free. Production `createContext` always supplies it. Direct fixtures do not constitute an HTTP path or activation proof.

## Covered policies

The live audit records 27 `circles_app` tables and a separate bigint `circles_publish.postPublishReceipts` relation within the 43-table private catalog. This candidate replaces the permissive runtime policy/policies on these **18 `circles_app` tables**, plus the receipt relation:

| Area                      | Tables/actions now protected by RLS                                                                                                                                                                                                                                                                                       |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Profile and circles       | `profiles` own writes; `circles` actor-owned/manager writes while preserving current listing/teaser reads; `memberships` self request/leave and manager changes                                                                                                                                                           |
| Social resources          | `posts` public/global and approved-member reads plus author/manager writes; `comments`, `reactions`, `bookmarks`, `follows`, `reports`, and `socialUploads` use actor/resource predicates                                                                                                                                 |
| Direct messages           | `conversations`, `conversationParticipants`, and `messages` require current participation for existing-resource reads/writes. Participant bootstrap is limited to an approved circle member adding themself or the exact two IDs encoded in a direct thread’s `directKey`; an arbitrary self-insert cannot create access. |
| Activity/moderation       | `activityItems`, `activityPreferences`, `activityCirclePreferences`, `moderationCases`, and `moderationActions` are recipient/current-circle-manager scoped while retaining service-created event flows                                                                                                                   |
| Durable publication retry | `circles_publish.postPublishReceipts` uses the existing bigint ID unchanged and is scoped to its `actorId`                                                                                                                                                                                                                |

Helpers fail closed for missing/malformed actor settings. The admin predicate reads the current private `users.role` under narrowly search-pathed `SECURITY DEFINER` helpers; it does not trust a request role. Existing `circles_admin_native_executor` and other native/admin policies are not dropped or broadened.

Two narrow runtime-role triggers complement RLS where PostgreSQL policies cannot compare `OLD` and `NEW` values: a non-admin/system runtime actor cannot transfer a Circle owner, and only the Circle owner may change membership roles except that an existing manager may approve `pending → member`. The triggers leave non-runtime native/admin execution unchanged.

The local drill verifies: no-context denial; guest global/public post discovery; approved-member private post access; non-member private-post refusal; cross-actor message insertion/refusal; arbitrary conversation self-join refusal; moderator self-promotion refusal; cross-actor upload/activity/receipt refusal; concurrent actor isolation; and cleanup that leaves no usable actor setting.

## Explicitly not covered

This is not a claim of full 43-table enforcement. The following 9 current `circles_app` tables retain their existing runtime policies in this candidate: `_dataMigrations`, `activeHostLeases`, `applicationSessions`, `liveChat`, `liveSignals`, `liveViewers`, `socialSeedMarkers`, `streams`, and `users`.

The remaining private catalog relations outside the covered set—including identity/provider-link, operations/admin, media/prompt/device, and any catalog relation not named in the SQL preflight—also retain current policy behavior. Their action inventory needs a separately selected system/owner model; they must not be silently given a broad `system` escape. In particular, OAuth/session persistence, email identity linking, encrypted-media proxy reads, operational health, import markers, live lifecycle state, and native administration are not closed by this candidate.

Direct Express routes and pre-context SDK/session calls do not yet carry this tRPC actor transaction: OAuth/email auth routes, `/api/media/*`, session/identity stores, readiness/health paths, and any future direct `getDb()` consumer require parent-owned composition or a deliberately separate native/system policy review before activation. The current actor-scoped tRPC request flow is real source integration, but local testing did not use real OAuth or HTTP because no real accounts/credentials/production fixtures are authorized.

## Activation gates owned by the parent/operator

Do not apply the SQL until all of the following pass:

1. Integrate the candidate with the final direct Express, OAuth/email identity, media, session, live, scheduler, and admin/native consumer inventory; give each an explicit authorized actor/system/native path or keep its table out of the replacement set.
2. Update and locally verify the parent-owned exact audit/health/recovery/readiness policy inventories. Current metadata contracts expect the old `runtime_* USING true/WITH CHECK true` names and will intentionally detect this SQL as drift until composed.
3. Re-run the source-equivalent HTTP→tRPC→service→PG17 drill with test-only authentication outside shipped code, including current nested transaction/lock-order cases and every covered router family.
4. Compare fresh read-only target metadata against the SQL preflight, current 43-table/private-schema inventory, current bigint receipt contract, detached `circles_app_login NOLOGIN` state, and existing admin/native policies. Do not query application rows.
5. Obtain explicit owner approval for the exact gated SQL transaction, DB-02 credential/runtime prerequisites, rollback plan, and authorized maintenance window. Then apply at most once and perform only approved read-only postflight checks.

## Reproduction

All commands are credential-free and use an empty inherited environment:

```sh
env -i PATH="$PATH" HOME="$HOME" CI=1 \
  pnpm vitest run tests/remaining-db03-actor-context.test.ts \
  tests/database-remediation-db03.test.ts tests/schema-connection.test.ts

env -i PATH="$PATH" HOME="$HOME" CI=1 pnpm check

env -i PATH="$PATH" HOME="$HOME" CI=1 \
  CIRCLES_REMAINING_DB03_LOCAL_PG17=1 \
  pnpm tsx operations/tests/remaining-db03-actor-rls.pg17.mjs
```

The PG17 runner accepts no DSN, starts a unique loopback-only synthetic cluster, creates only synthetic roles/rows, uses bounded connection/startup operations, closes clients/pool/server in `finally`, and removes its temporary directory. It is a local RLS/transaction proof, not provider, real-account, native, OAuth, media, or production authorization evidence.
