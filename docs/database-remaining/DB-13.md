# DB-13 — Provider gateway evidence boundary

## Scope and current result

This candidate adds `scripts/remaining-db13-gateway-capture.mjs` and its focused credential-free test. It is a read-only syntax, freshness, binding, and gateway-consistency diagnostic for the Supabase Data API gateway of project `vvclcsqletcxzoaayqzq`.

It does **not** change an exposed-schema list, the provider’s automatic-exposure control, a database schema, grants, RLS, policies, settings, credentials, backups, schedules, application code, or provider account. It does not use a browser, a database connection, or an owner session itself.

The fresh audit’s seven zero-row private-schema probes returned `406` / `PGRST106`; that verifies an observed current rejection only. It does not establish the provider setting that automatically exposes future tables/functions. DB-13 therefore remains **UNKNOWN**.

A `--capture-file` result is always top-level `unknown` with reason `ATTESTED_CAPTURE_NOT_INDEPENDENTLY_AUTHENTICATED`, even when the local JSON has the correct shape, pins the right project and Dashboard path, lists no `circles_*` schemas, and attests that automatic exposure is disabled. Its CLI exit code is `2`, never `0`; it cannot mark DB-13 closed.

## What a local attestation must contain

The tool accepts a private JSON **attestation** only when all of these finite facts are present and current:

- capture contract version `1`;
- provider `supabase` and the exact project ref `vvclcsqletcxzoaayqzq`;
- claimed source kind `authenticated_dashboard_settings` and source version `dashboard_api_settings_v1`;
- an ISO `observed_at` no more than **15 minutes** old and no more than one minute in the future;
- claimed HTTPS `GET` source origin `https://supabase.com`, path `/dashboard/project/vvclcsqletcxzoaayqzq/settings/api`, HTTP status `200`, and claimed authentication origin `supabase_authenticated_owner_dashboard_session`;
- a bounded, duplicate-free complete `exposed_schemas` array; and
- the Boolean `auto_expose_new_tables` value.

The project, transport origin/path, authentication-origin claim, source version/time, schema list, and automatic-exposure control are all mandatory. A wrong project, old capture, missing Boolean, alternate origin, self-asserted `reviewed` marker, malformed schema list, or missing HTTP/authentication metadata is rejected as `UNKNOWN`.

Passing those checks means only that the local literal is syntactically valid and suitable for bounded review/probe binding. It does **not** prove that a human was authenticated to Supabase, that a Dashboard rendered the values, or that the values came from any provider response. JSON provenance labels are claims controlled by the file supplier. The report intentionally separates:

1. `local_capture_syntax` — the bounded parser accepted the local shape;
2. `provider_authentication` — always `unknown` for a supplied file, with reason `ATTESTED_CAPTURE_NOT_INDEPENDENTLY_AUTHENTICATED`;
3. `attested_*` values — the local values’ internal safe/unsafe interpretation, still `unknown` as provider facts; and
4. `settings_to_gateway_schema_probes` — a separate effective-route consistency observation, never Dashboard authentication or toggle proof.

4. Retain contemporaneous original controlled proof outside this program: either the actual authenticated Dashboard observation/screenshot or a provider-owned authenticated API response that visibly binds the project and supplies **both** controls. ### Parent-only independent attestation (outside the program)

The parent, not this script, may independently assess contemporaneous controlled proof from the authenticated Dashboard or a provider-owned authenticated response. That review must verify the actual project binding, complete exposed-schema list, automatic-exposure control, and observation time directly in the original proof. The parent may then record an evidence-based human conclusion through its controlled evidence process.

Do **not** add `reviewed`, `authenticated`, `verified`, or any comparable Boolean to the local JSON to simulate this review. The script deliberately has no input field that can promote a file to provider-authenticated or `PASS`.

## Legitimate Management API transport: partial only

The established Management API PostgREST endpoint is pinned in the script to:

```text
GET https://api.supabase.com/v1/projects/vvclcsqletcxzoaayqzq/postgrest
```

With a protected runtime injection of `CIRCLES_SUPABASE_MANAGEMENT_API_TOKEN`, an authorized parent may run:

```bash
# Token injection is parent-owned. Do not paste a token into shell history or source.
node scripts/remaining-db13-gateway-capture.mjs --management-api
```

The command makes exactly one redirect-refusing, 5-second-bounded `GET`, accepts a response no larger than 64 KiB, pins the token to a Bearer header in memory, and reports only redacted results. It validates the documented response shape and extracts the exposed schema list.

That documented response does **not** attest `auto_expose_new_tables`. Therefore:

- a listed `circles_*` schema is a real **FAIL** for that directly authenticated, partial response;
- no listed `circles_*` schema is still **UNKNOWN**; and
- an unavailable/malformed response, missing token, rejected authentication, or missing provider endpoint is **UNKNOWN**.

This partial transport must never be combined with a guessed toggle, a local Dashboard literal, or a review Boolean to create `PASS`.

## Optional settings-to-gateway consistency probes

With a separately protected public anon key injected in `CIRCLES_DB13_PUBLIC_ANON_KEY`, the parent may append `--public-probe` to either supported source mode:

```bash
# Parent-owned protected injection only; the key is not accepted as an argument.
node scripts/remaining-db13-gateway-capture.mjs \
  --capture-file /private/circles/DB-13-provider-settings.json \
  --public-probe
```

The script issues bounded `GET .../rest/v1/__circles_db13_schema_probe__?limit=0` requests only against the exact pinned project URL, using `Accept-Profile` for the finite observed private-schema set:

- `circles_app`
- `circles_admin`
- `circles_auth`
- `circles_ops`
- `circles_publish`
- `circles_identity`
- `private`

No caller-controlled URL, relation, schema, token argument, redirect, or row query is allowed. A `406` response with `PGRST106` is counted solely as rejection of that current schema route. Probe evidence is SHA-256-bound to the exact timestamped settings capture, so stale/replayed probe results are rejected. A non-rejected or settings-mismatched private-schema route is recorded as a **probe-consistency failure**.

All `406` / `PGRST106` probes remain **partial evidence**. They do not make the automatic-exposure control known, do not establish Dashboard authentication, and do not promote a local attestation from `UNKNOWN` to `PASS`. A local-file report stays `UNKNOWN` even when every bound probe is consistent; a probe failure remains visible in its individual check.
