## Proposed policy recorded as inactive

Installation would create a `circles_ops` singleton policy, hold registry, append-only sanitized run history, and a PostgreSQL-admin-only status view. Its inserted state is exactly:

| Item                        | Candidate value                                                               | Activation state       |
| --------------------------- | ----------------------------------------------------------------------------- | ---------------------- |
| OAuth pending state         | Eligible only when `expires_at <=` one captured `clock_timestamp()`           | Proposed, **INACTIVE** |
| Normal application session  | Eligible only when expired for at least 90 days                               | Proposed, **INACTIVE** |
| Revoked application session | Eligible only if already expired and revoked for at least 180 days            | Proposed, **INACTIVE** |
| Batch                       | 1–100 candidates per state kind; default 25                                   | Enforced for dry runs  |
| Locking                     | expiry order plus `FOR UPDATE SKIP LOCKED`; 500 ms lock / 5 s statement limit | Enforced for dry runs  |
| Destructive deletion        | `false`                                                                       | **INACTIVE**           |
| Recurring schedule/cadence  | `false` / `NULL`                                                              | **INACTIVE**           |

The application-session predicate always starts with `"expiresAt" <= v_now`. A still-active session cannot be selected even if its `"revokedAt"` is older than 180 days. The OAuth predicate is independently bounded to the same captured `v_now`. Both relations preserve their primary/session fingerprint keys and revocation columns; neither source relation is altered by installation.

The placeholder configuration is intentionally not approval. The policy cannot transition to `active` without a nonblank owner approval reference, explicit destructive enablement, an object-shaped confirmation payload, and a separately selected schedule cadence if scheduling is desired. The helper independently rejects `p_dry_run => false` unless that future active state and exact stored private confirmation are present. A call labeled `scheduled` is rejected unless the policy is active with both schedule enablement and cadence selected.

## Hold and audit design

An explicitly entered active hold suppresses candidate selection before locks or deletion for its scope. Allowed scopes are:

- `all` — protects both OAuth pending state and application sessions;
- `oauth_pending_states` — protects only OAuth pending state; and
- `application_sessions` — protects only durable application sessions.

Hold reasons are limited to `incident`, `legal`, `support`, `user_deletion`, `jurisdictional`, or `other`; each requires an external reference. A released or expired hold is no longer active. The helper takes a bounded table lock on the small hold registry, so a newly recorded hold cannot race between hold evaluation and state-row selection.

Every completed invocation writes only policy/version, timing, mode, batch, hold booleans, aggregate candidate/deletion counts, and result status to `circles_ops.remaining_db16_security_state_retention_runs`. The admin-only `circles_ops.remaining_db16_security_state_retention_status` view makes the configured horizons, active hold counts, and sanitized last result observable. It intentionally omits OAuth state values, session fingerprints, owner approval reference, and private confirmation data.

## Manual dry-run operator path

The helper has no application route, browser capability, or runtime privilege. `postgres` alone has `EXECUTE`; browser roles, service role, app/runtime/admin roles, and the detached NOLOGIN app role are explicitly denied. The candidate also refuses an install if a named DB-16 Cron job or an existing cron command referencing the helper already exists. It does **not** call `cron.schedule`, `pg_cron`, or any external scheduler API.

`scripts/remaining-db16-lifecycle.mjs` is an operator tool, not an installer. It never reads `.env`, an inherited DSN, or an implicit PostgreSQL environment setting. It requires a private, regular, mode-0600 file containing exactly one PostgreSQL URL when a connection is requested. It defaults to manual dry-run mode with batch 25:

```bash
node scripts/remaining-db16-lifecycle.mjs \
  --database-url-file /private/circles-db-url
```

To inspect the safe default without connecting anywhere:

```bash
node scripts/remaining-db16-lifecycle.mjs --print-sql --batch-size 25
```

A later deletion invocation needs all of the following, none of which is granted here: a separate approved active policy installed by the parent, a private mode-0600 confirmation JSON file containing `schema`, `policyVersion`, `approvalReference`, and an object `confirmation`, plus both `--delete` and `--acknowledge-db16-destructive-operation`. The CLI sends only the confirmation object; the database helper also compares it to the stored policy. This extra local confirmation cannot itself enable a policy or schedule a job.

## Separate proposed 03:45 UTC activation/schedule candidate

The separate action candidate proposes one daily **03:45 UTC** (`45 3 * * *`) batch-25 execution only if the owner later selects that cadence and authorizes destructive scheduling. It is not part of installation and is inactive until the owner selects and applies it through a separately controlled PostgreSQL workflow.

It must run directly as `postgres` and requires all four transaction-local custom settings, deliberately absent from this repository:

- `circles.db16.retention_activation_ack` — an exact owner-selected acknowledgement string;
- `circles.db16.retention_owner_approval_reference` — the selected owner approval reference;
- `circles.db16.retention_policy_version` — a non-placeholder policy version; and
- `circles.db16.retention_confirmation` — an object JSON value whose `activation_ack` exactly equals `circles.db16.retention_activation_ack`.

The equality is an exact operational guard, not approval evidence and not a real owner approval by itself. No fixture token, source string, local test value, or GUC name constitutes approval. The separate owner/legal/security decision and protected operational record remain required.

Before any mutation, the action candidate requires the actual installed `pg_cron` extension in the `cron` schema, its real `cron.schedule(text,text,text)` API, the reviewed `cron.job` catalog columns, the exact untouched inactive policy, no existing DB-16 helper-referencing job, and the exact unchanged Cron 7 health sentinel. It does not create `pg_cron` and never inserts directly into `cron.job`. Only after those guards does it update the singleton policy to active and call the real `cron.schedule` API.

The proposed stored command invokes the helper with `p_dry_run => false`, source `scheduled`, and batch 25. It gets the already-stored exact confirmation from the protected policy row rather than embedding that payload in `cron.job.command`. Postflight verifies the exact schedule, command, database, `postgres` job owner, active state, and unchanged Cron 7. The candidate remains unapplied here; no schedule exists as a result of this work.

## Local validation — synthetic-only destructive proof

The isolated proof uses no provider, browser, production DSN, real account, service restart, shared fixtures, or persistent approval material:

```bash
env -i PATH=/usr/bin:/bin HOME=/tmp CI=1 /usr/bin/python3 -B \
  operations/tests/remaining-db16-lifecycle.pg17.py --local-pg17
```

It creates a temporary PostgreSQL 17 cluster bound only to `127.0.0.1` with synthetic deterministic hashes. It first verifies the installed policy stays inactive and rejects `p_dry_run => false` and scheduled source. It then explicitly updates **only that disposable policy row** to an unmistakably synthetic-only active shape and invokes the real helper with `p_dry_run => false`.

That synthetic destructive proof verifies all of the following without printing source identifiers:

- OAuth expiry deletion count; normal-session 90-day deletion count; revoked-session 180-day deletion count; and still-active long-revoked session preservation;
- actual hold protection for `all`, `oauth_pending_states`, and `application_sessions` scopes, including the opposite scope’s controlled deletion;
- destructive `SKIP LOCKED` concurrency: locked OAuth/session rows remain until their second transaction releases them;
- real maximum batch 25 and maximum batch 100 deletion behavior, with 101 eligible rows leaving one and batch 101 rejecting;
- sanitized audit and status output containing aggregate counts/hold result only, with no OAuth state fingerprint, session fingerprint, account/application identifier, owner reference, or confirmation payload;
- the `postgres`-only ACL and in-function `session_user` guard; and
- rejection of a lookalike `cron` table because the separate schedule candidate requires the actual `pg_cron` extension/API, with Cron 7 unchanged and no DB-16 job created.

The temporary policy row’s constraint-satisfying reference and confirmation exist solely to exercise the helper in a process-local cluster that is destroyed at cleanup. They are not a real owner approval, cannot activate a real policy, and are not evidence that owner privacy/retention choices have been made. The proof has **not been run against production**.
