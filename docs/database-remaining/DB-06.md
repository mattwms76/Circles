# DB-06 — provider-admin future-function default ACL

## Scope and authoritative evidence

DB-06 is a narrow hardening candidate for **future** functions created by the provider-managed `supabase_admin` role. It does not change an existing routine, an application row, role membership, a runtime login, an RLS policy, a schema grant, a schedule, or any type/role default ACL. If the real provider object owner decides the risk is approved and supplies an authorized executor, the candidate contains only this one global mutation:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE supabase_admin
  REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC;
```

Fresh read-only provider evidence at `2026-10-28T16:16:53Z` records the exact current state:

- `executor_role=postgres`, `executor_is_superuser=false`, and the executor is **not** a member of `supabase_admin`. Consequently, `executor_can_alter_target_defaults=false` is a current blocker. It is not permission to grant membership, use `SET ROLE`, bypass the assertion, or hide a failed audit.
- `supabase_admin` is a provider superuser and has effective `CREATE` in `circles_app`; `postgres` owns `circles_app`.
- There are **zero global** `supabase_admin` `FUNCTION` default-ACL records. PostgreSQL's generated built-in global default consequently gives `PUBLIC` non-grantable `EXECUTE` on future `supabase_admin` functions.
- There are **exactly six** legitimate provider-managed schema-additive `FUNCTION` records. They are part of the approved baseline and DB-06 must preserve them byte-for-byte.
- Separate type defaults and all unrelated role/schema records remain outside DB-06.

A global `ALTER DEFAULT PRIVILEGES` override replaces the PostgreSQL built-in global default. A matching `IN SCHEMA` default ACL is additive, so a schema-only revoke cannot remove the effective global `PUBLIC EXECUTE`. The possible correction therefore has an unavoidable provider-wide future effect; the six schema entries do not narrow that blast radius.

## What the executable transaction does

The transaction fails closed unless the exact fresh baseline still holds. In one short transaction it:

1. Requires `supabase_admin` to remain a provider superuser and eligible `circles_app` creator.
2. Requires the executor to be the target role, a legitimate target-role member, or a superuser. It does not grant membership, call `SET ROLE`, or treat `CREATEROLE` as sufficient authority.
3. Requires **zero global** target `FUNCTION` entries, **exactly six** schema-additive entries with the ACL texts above, and the generated built-in `PUBLIC EXECUTE` global default. A missing, added, or changed schema entry is a refusal, not something DB-06 repairs.
4. Snapshots every unrelated default-ACL record transaction-locally, executes the one global `REVOKE`, and never changes a schema-additive or type default.
5. Requires exactly one new global target `FUNCTION` record with no `PUBLIC EXECUTE`, then verifies the six schema records and every unrelated ACL remain equivalent before commit.

Existing routines retain their ACLs. Future routines made by `supabase_admin` begin with no global `PUBLIC EXECUTE`; an intended caller needs a deliberate explicit per-routine `GRANT EXECUTE` after creation. DB-06 does not suppress a failed security auditor. The parent must rerun the normal security audit afterward and leave any separate DB-13 gateway finding or other audit failure visible.

The verified current source/private schema still has explicit `PUBLIC` revokes for existing private routines. DB-06 preserves those routines and the approved 43-table/current 9-admin-table, 23-admin-function, 117-policy, bigint-receipt, and detached `circles_app_login` NOLOGIN state.
