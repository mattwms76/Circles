# Circles comprehensive security audit — 29 October 2026

## Executive conclusion

This synthesis reconciles seven independent review domains against the source baseline **`98587dd128c984aac98538c06fabd61677770238`** (tree **`fcc68acf9d17017df6bd6056aee6534234275a86`**) on `feature/security-audit-roadmap-2026-10-29`. It is a source-and-artifact review, not a production penetration test or a certification that Circles is secure.

The reconciled register contains **30 unique items**: **4 custom source-confirmed findings**, **1 source-traced installed dependency advisory**, **19 conditional risks**, and **6 verification gaps**. Source-confirmed findings include an architectural revocation limit, not four reproduced external exploits. The resulting contextual ratings are **1 high, 17 medium, 6 low, and 6 informational**. These ratings are not a count of dependency paths: the package audit reports **four advisory families** (one low, one moderate, and two high according to the tool), with the same family/version set in full and production installs. The 377 dependency paths reported by the tool are alternative graph paths, not 377 vulnerabilities.

The most important source work is to prevent an active session from enrolling a durable attacker-controlled email identity (**AUTH-001**), stop direct-message creation from publishing an unprofiled recipient’s private-source name (**ACCESS-001**), and address live-video revocation/abandoned-signaling design (**LIVE-001**, **LIVE-002**). The only high-rated item is conditional: a signing-secret compromise or uncoordinated rotation also affects historical encrypted media because the media key is derived from that signing secret (**MEDIA-001**). Deployment, database, provider, native-device, TURN, recovery, and ingress assumptions must still be verified separately.

## What was assessed

The source review covered authentication, OAuth, cookies, email identity, durable sessions, protected social/circle/activity/moderation access, database roles and RLS, media encryption/upload/proxy controls, HTTP admission/CORS/proxy trust, live signaling/TURN/client lifecycle, CI/recovery/supervision, and installed dependency consumers. Reviewers also read relevant migration and operational contracts and exercised targeted isolated tests. No repository behavior was treated as deployed merely because a migration or template exists.

The scan baseline records 980 tracked files and 175 reachable commits. The completed JUnit XML and aggregate log agree: **244 test files and 1,209 tests passed, with zero failures or errors**. The separate synthetic-auditor suite had **71 passes, zero failures, and one skip across 72 tests**; the skipped case is not a pass. TypeScript with unused-code checks, zero-warning lint, formatting, environment-template/CI checks, and API compilation passed. Focused domain subsets overlap the full suite and are not added to its total. These checks are not evidence of live database semantics, browser cookies, native cache behavior, an Internet-facing API, provider configuration, real WebRTC, TURN allocation, backup restoration, or a signed mobile release.

## Reconciled priority findings

### P0 source findings

**AUTH-001 — Medium / source-confirmed — Durable email credential enrollment lacks fresh primary authentication.** When the optional email-auth feature is enabled, a valid Circles session alone can authorize the email-connect flow (`server/_core/email-auth.ts:891-931`); the resulting verified email subject mapping is durable (`server/_core/email-identity.ts:329-375`). A session thief who controls a confirmed provider email identity could attach it and preserve access after the stolen session expires or is revoked. Require a short-lived, single-use, actor-bound recent-primary-authentication intent for enrollment, plus credential inventory/removal/recovery and notification behavior. Acceptance requires isolated stale, replayed, mismatched-actor, success, removal, and revocation tests, followed by an authorized synthetic-account staging exercise. The review did **not** establish whether email authentication is enabled in deployment or contact the provider or an account.

**ACCESS-001 — Medium / source-confirmed — Opening a direct conversation can publish an unprofiled recipient’s private-source name.** `social.openDirect` accepts a caller-selected target (`server/social-router.ts:762-764`) and materializes profiles for both actors after only checking target existence (`server/social-service.ts:3161-3170`). Profile materialization reads `users.name` and persists a public profile (`server/social-service.ts:548-579`), while public profile endpoints enumerate and return profiles (`server/social-router.ts:518-544`; `server/social-service.ts:863-894`). An authenticated user who knows a valid numeric target ID can create an unsolicited conversation and make a formerly absent profile discoverable; the path does not expose email, OpenID, session, or other `users` fields. Define a DM consent/identity model and use conversation-scoped display data or require recipient opt-in/an existing public profile. Regression acceptance must prove guest profile reads cannot reveal an absent target’s private-source name after a DM-open, including retry/concurrency and nonexistent-target cases.

**LIVE-001 — Medium / source-confirmed design limitation — Direct WebRTC delivery is not server-revocable after negotiation.** The server provides a membership-filtered peer-authority snapshot to the host (`server/live-router.ts:746-795`), but web/native adapters create direct peer connections and close them locally (`components/live-media.web.tsx:465-498,542-575`; `components/live-media.native.tsx:663-698,744-774`). A removed viewer may continue receiving a negotiated private feed if the host is compromised, deliberately ignores revocation, or loses control-plane connectivity while the peer transport remains alive. This is a limitation of the documented direct-P2P architecture, not an unauthenticated join bypass; no media architecture can prevent a malicious sender from independently redistributing content. Decide whether server-enforced termination of the app-managed transport is a product requirement. If it is, plan mediated SFU/media-proxy delivery with revocable transport authorization; otherwise constrain/document the direct-P2P feature. Acceptance is an adversarial post-negotiation removal test in an approved real WebRTC environment.

**LIVE-002 — Medium / source-confirmed — Abandoned streams retain bounded signaling payloads without automatic cleanup.** A stream can retain up to 512 × 32,768-byte signals (`server/live-router.ts:54-66`). Explicit end deletes signals, while expired-host handling only marks a stream ended (`server/live-router.ts:499-601`); cleanup is only attempted during later stream operations and no matching baseline index is present (`server/live-router.ts:874-893`; `drizzle/live-schema.ts:70-83`). A live-enabled account can repeatedly abandon filled streams, increasing retained database data and poll cost. Add automatic abandoned-session cleanup, aggregate storage retention/budgets, and poll/deletion indexes. A disposable PostgreSQL retention/query-plan test is required before activation.

### High-impact conditional design risk

**MEDIA-001 — High / conditional-risk — Signing-secret coupling gives one secret media-wide consequences.** Media encryption and decryption derive the AES-GCM key from the managed signing secret (`server/social-service.ts:180-236`; `server/_core/env.ts:71-80`). An attacker needs both that secret and ciphertext objects for confidentiality impact, while an uncoordinated signing-secret rotation can make historical objects unreadable. Design a separately managed versioned media root key, key identifiers, dual-read migration, recovery procedures, and rotation tests. Do **not** rotate the signing secret as a generic logout response. This needs separate credential/key-custody approval before any provider or production action.

### Dependency advisory reality

The fresh full and production `pnpm audit --json` artifacts both exit 1 and contain the exact same four families: `decode-uri-component@0.2.2`, `node-forge@1.4.0`, `zod@3.25.76`, and `deepmerge@4.3.1`. Full audit reports 1,258 installed dependencies; production reports 850. This proves graph retention, not runtime exploitability.

**DEP-001 — Medium / source-confirmed reachability — Decoder denial-of-service exposure is source-traced through an attacker-controlled deep-link path.** `expo-router@57.0.22` reaches `query-string@7.1.3` and `decode-uri-component@0.2.2` (`pnpm-lock.yaml:3098-3100,11695-11700`); the installed Router parser calls `queryString.parse` on route parameters, and Circles registers a browsable custom Android URI scheme (`app.config.ts:24-27,70,89-101`; `app/oauth/callback.tsx:93-101`). A malicious percent-encoded deep link can therefore affect client/web availability. The applicable upstream advisory describes availability impact, not confidentiality, integrity, or code execution.[1] Qualify a compatible Expo Router/Expo SDK parent migration that removes the affected graph; do not add a decoder wrapper or CommonJS bridge. Require a frozen-lock install, a fresh production audit, and bounded hostile deep-link regression tests.

**DEP-002 through DEP-004** are conditional tooling/build risks, not confirmed server/API exposure: Expo CLI retains transitive `zod@3.25.76` ([2]); Expo code-signing tooling retains unpatched `node-forge@1.4.0` ([3]); and Expo configuration merging retains `deepmerge@4.3.1` ([4]). The direct application `zod@4.6.7` is separately above the advisory fixed floor. Keep configuration/CI inputs trusted, wait for qualified parent releases or a planned SDK migration, and do not force incompatible child upgrades or replace cryptographic parsing locally. **DEP-005** records that the checked-in dependency register is stale against the fresh raw audit: it omits deepmerge and still lists a historic non-emitted cache advisory.

## Conditional deployment and ownership gates

These are meaningful risks only when their explicit operating conditions hold; static source does not establish those conditions.

- **Account and HTTP admission:** remote HTTP frontend origins remain syntactically configurable for credentialed CORS/OAuth/email flows (**AUTH-002**); email throttles are deliberately per-process (**AUTH-003**, cross-reference SEC-023); distributed edge limits and trusted-forwarded-header replacement are not evidenced (**HTTP-001**, **HTTP-002**, cross-references SEC-010/016/023/024); and a publicly exposed development-mode process could disclose an uncaught Express stack (**HTTP-003**).
- **Database boundary:** the active pool’s bootstrap principal remains more powerful than the runtime role (**ACCESS-002**, SEC-020), and current runtime-role RLS is a trusted-server boundary rather than per-user/per-circle row isolation (**ACCESS-003**, SEC-019/027). Neither is a direct browser database-access finding. Both require owner-approved role/RLS design and read-only live catalog attestation. **ACCESS-004** is the companion verification gap: SQL files and static tests cannot prove migration journal, ACL, role, policy, function, or force-RLS state.
- **Media and storage:** there is no source-level provider delete/compensation lifecycle for opaque objects (**MEDIA-002**, CBA-06); account replacement does not await cache eviction before admitting the new actor (**MEDIA-003**, CBA-05/SEC-008); and provider object ACLs, deployed DNS/TLS/CDN behavior, ledger readiness, device cache/decoder behavior remain unproven (**MEDIA-004**, SEC-006/007/008/015).
- **Live relay/privacy:** TURN credentials are actor-bound but not bound to a session, stream, or membership revocation (**LIVE-003**); adapters do not set relay-only ICE policy (**LIVE-004**), so participant-address exposure depends on product policy and runtime candidate behavior.[5] Applied status of the prepared live-chat indexes is unknown (**LIVE-005**).
- **Operational custody:** recovery/key artifacts are not equivalently excluded from Git staging (**OPS-001**, SEC-025/026, CBA-06); the supervisor forwards the server environment to Metro by default (**OPS-002**, CBA-07); privileged/recovery helpers resolve commands through inherited `PATH` (**OPS-003**, CBA-08); and the locked install has no minimum-publication-age policy (**OPS-004**). An actual encrypted restore drill remains an explicit evidence gap (**OPS-005**).
- **Provider evidence:** confirmation, recovery, disable/delete, rate-limit, and redirect configuration for the email provider were not inspected (**AUTH-004**). This is not a finding that the provider is misconfigured.

The complete item-by-item evidence, preconditions, impact, remediation, acceptance criteria, reachability, and prior SEC/CBA references are in [`security-findings-20261029.json`](security-findings-20261029.json).

## Controls substantiated in source

The review did substantiate several important source controls: OAuth state is random, HMAC-protected, cookie-bound, short-lived, persisted as fingerprints, and atomically consumed; the native OAuth receiver is fixed and state/generation-bound; durable sessions are actor-bound, hash-addressed, capped, revocable, and fail closed; logout revokes presented credentials and fences stale client credential admission; email identity mapping is unique and confirmation-gated; protected social/activity/circle/moderation paths recheck actor/membership scope; media transport has strict origin, DNS, TLS, redirect, size, cancellation, and final authorization rechecks; and CORS reflects only exact configured origins.

These controls reduce exposure but do not erase the findings above or prove real deployment behavior.

## Limitations and evidence boundaries
